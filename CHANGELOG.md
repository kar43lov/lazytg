## [Unreleased]

### Fixed

- **A dropped connection ended the session for good.** `ReconnectManager` was built by `AttachClient` and started by nobody: `Run` had no caller in production, so the state machine that owns offline → connecting → online never ran. Underneath it, `reconnectAdapter.Connect` returned `nil` without doing anything, so even when the manager did run it was told a dead session had been repaired. The combination cost more than reconnection: `ReconnectManager` is the only publisher of `events.ConnectionStateChanged`, so the status indicator never moved after the seed value the initial attach wrote — the green "online" survived pulling the network cable. Now the MTProto run loop lives in a supervisor (`cmd/lazytg/cmd/session.go`) that can stand a fresh session up, `Connect` delegates to it, and the manager runs for the lifetime of the session. An adapter with no supervisor behind it returns an error rather than `nil`, because a manager that believes it reconnected publishes "online" over a session that is gone — the one outcome worse than staying offline.
- **Two defects the reconnect work created, both found in review and both fatal to it.** First: gotd's `telegram.Client` is single-use — `Run` cancels the client context on the way out, so a second `Run` returns `client already closed` without sending a packet. A supervisor that restarts sessions on one gotd client would have failed every attempt forever and reported it as a network problem. The client is now rotated per session, with `Client.API()` kept as one fixed object over a swappable invoker: services capture it at attach and the panes capture those services at construction, so replacing the object underneath them would be a data race against the Bubble Tea goroutine. Second: standing a new session up tears the old one down, and that teardown reports itself on the same disconnect channel the manager is about to read again. `context.Canceled` reads as user-initiated shutdown, so the manager returned after its first successful reconnect and recovery worked exactly once per process; a teardown carrying a plain error instead sent it into a cycle of tearing down the session it had just recovered — measured at 1.27 million reconnect attempts in 200 ms against fakes, which on a real account is a login storm on a client Telegram already watches. Both are pinned by tests that fail with exactly those symptoms when the fix is removed. A fourth, and the one that mattered most for ban-risk: a teardown that did not finish inside the grace period was a warn line and nothing else, so `Restart` went on to open a new session while the old run loop still held a connection. Two run loops on one account are two devices logging in, on a client Telegram already watches for being unofficial, and a flapping link produces the situation over and over. Restart now refuses, with a retryable error, so the manager waits the old session out instead. A third, found by the third review engine: the gap-recovery goroutine was cancelled but never joined, while the update manager is shared across sessions — so the next session could reset the manager's state while the previous run's goroutines were still writing pts to the same rows. The session is not considered gone until that goroutine has returned.
- **The connection indicator only ever knew what lazytg did, not what the connection did.** gotd reconnects on its own while `Run` is executing, and it never returned in that case, so an entire outage was invisible. gotd 0.161's `OnConnectionState` closes that: `tg.Client` now exposes a one-slot state feed (latest wins — the callback runs synchronously on gotd's connection path and must not block), `ReconnectManager` pumps it onto the bus for as long as it runs, and repeats are suppressed so a flapping link does not wake every bus subscriber per event.
- **`--polling` did nothing.** The flag was parsed, stored in `app.Config` and read by no one, so a user who reached for it *because* live updates were not arriving got exactly the behaviour they were working around, silently. It now starts the fallback that has existed since Stage 2: the three most recently active chats, polled every three seconds, publishing only what is newer than what the mirror already holds. It runs alongside the push path rather than replacing it — the flag's own description said "instead of updates.Manager", which was never the useful behaviour. Three chats at three seconds is one request per second, and the cap is a ban-risk decision rather than a throughput one. The fallback's watermark now takes the higher of its own and the store's, so messages the live path already delivered are not republished on the next tick. Failures are logged as a streak rather than per tick: every poll fails for every polled chat while the connection is down, and one warn each is sixty lines a minute — enough to rotate the log file and carry off the diagnostics that explain the outage. And polling now publishes through the same duplicate filter the live path uses, which is the only thing that can close the overlap between them: the source reads the store's newest id, then the poll makes a network call, and a live update landing in that window is newer than the watermark the call went out with — so the message would be shown twice. One filter across both paths makes "appears exactly once" true rather than likely.

### Added

- **Gap recovery: `updates.Manager` is wired.** Everything for it existed and was tested — `sqlite.StateRepo` implementing `updates.StateStorage`, `UpdatesDispatcher.Manager` — and nothing used it, so a mid-session transport drop left the mirror and the dialog list agreeing with each other and both stale. The manager is now the client's update handler, with the peer table as its channel access-hash store: it loads a channel's stored pts only when it can also find that channel's access hash, so the in-memory default would have quietly reduced recovery to private chats and basic groups after every restart. `MaxChannelDifferenceConcurrency` (new in gotd 0.161) is capped at 4 — recovery costs one `updates.getChannelDifference` per channel, and firing all of them the moment a connection returns is both rate-limit bait and a traffic shape no human client produces. The wiring is deliberately failure-tolerant: gotd documents `Handle` as forwarding updates as-is when `Run` has not succeeded, so a `getState` or storage failure costs ordering and gap recovery while live updates keep arriving, and the session is held open with the reason logged rather than torn down.
- `lazytg --polling` is documented in `README.md`, `docs/CONFIGURATION.md` and `docs/ARCHITECTURE.md` as what it now is, and `docs/MANUAL_SMOKE.md` gains a step that actually checks it (the previous one said the flag was a no-op and told the tester to skip).

### Security

- **The release toolchain is pinned to a patched Go.** `go.mod` declared `go 1.25.0` and nothing else, and every workflow installs from `go-version-file: go.mod` — so binaries shipped with whatever that resolved to, and `govulncheck` reported nine standard-library vulnerabilities reachable from this code, among them two in `crypto/tls`, one in `crypto/x509` and one in `net/http`. That matters for a client whose whole job is holding a long-lived TLS connection to a server it does not control. A `toolchain go1.26.6` directive takes the count to zero, verified by re-running the scan; the language version stays at 1.25 so nothing about the source changes. Of the remaining findings none is called by this code, and after the dependency sweep above none is in a third-party package at all.
- **A revoked authorisation no longer reconnects in a loop.** A session revoked from another device fails every attempt in exactly the same way, so treating it as retryable had the reconnect manager re-offer a dead auth key every backoff period for as long as the TUI stayed open. It is terminal now: the supervisor closes itself and the manager stops. Repeatedly presenting credentials Telegram has already invalidated is the kind of behavioural trace this project exists to avoid.

Verified locally: `go build ./...`, `go test ./...`, `golangci-lint` 2.12.1 (0 issues) and `goreleaser check` all pass on the combined set.

## [0.1.0-alpha.1] - 2026-08-18

First tagged build. Alpha: the pipeline that produces it has never run before this
tag, and the client itself has one live session behind it. Bring your own
Telegram API credentials (`LAZYTG_API_ID` / `LAZYTG_API_HASH`) and a test
account — see [docs/INSTALL.md](docs/INSTALL.md) and [docs/SECURITY.md](docs/SECURITY.md).

### Added

- **Text selection in the thread, with copy to the clipboard.** Drag to select, release to copy; a drag inside one message is character-exact, and the moment it crosses into another message both are taken whole — the rule Telegram Desktop uses, and the one the user asked for ("выделяется сразу несколько целиком, даже если ты не до конца довёл"). A double click takes the message under the pointer, which is the common case without a precise drag. The highlight is reverse video (the one attribute every terminal renders identically) applied with cell-accurate, ANSI-aware slicing, so surrounding styling survives and the visible text is unchanged — `TestApplySelection_HighlightsWithoutChangingText` pins exactly that. Line ranges per message come from the renderer itself (`renderContent` returns content and spans together) rather than a second implementation of the same layout, because the two would drift and the drift would read as "it selects the wrong message". Copying goes through OSC 52 (`tea.SetClipboard`) instead of shelling out to pbcopy/xclip: it is the terminal's own clipboard channel, so it works over ssh and inside tmux with `set-clipboard on`, and lazytg needs to know nothing about the host. Whatever is highlighted is what lands in the clipboard, header row included when the selection covers whole messages — a character-exact drag inside one message is there for lifting out the text alone. A highlight is a range of screen cells with no tie to the text under it, so it is dropped wherever that text is replaced: opening another chat by any route, and any resize, including dragging the separator, which re-wraps every line (`TestSelection_DroppedWhenTheChatChanges`, `TestResizeDropsTheSelection`). The pane's own title row is inert, and a drag that actually selected something breaks the double-click pair, so pressing again on the same cell starts a new selection instead of copying the whole message.
- **Chat cycling: `ctrl+tab` / `ctrl+shift+tab` (aliases `alt+n` / `alt+p`) open the next and previous chat from anywhere, including mid-sentence in the composer.** Wraps at both ends and follows the list's own order — pinned first, then by last message, the same order Telegram shows. Both are ordinary keymap actions (`next_chat` / `prev_chat` in `keymap.toml`). The aliases are not decoration: `ctrl+tab` only reaches an application in terminals that implement key disambiguation (the Kitty keyboard protocol), and elsewhere the terminal sends a plain `tab`, which focus cycling takes.
- **The composer takes focus when a chat is opened**, from the click, the Enter, the palette and the search jump alike, so picking a conversation and typing in it is one gesture rather than two plus a Tab.
- **The pane separator is draggable.** The split is kept as an absolute column count (a ratio would make the pane creep on every resize), clamped so neither pane can be dragged into unusability, re-clamped when the terminal shrinks, and highlighted while held — a one-column grab handle gives no other feedback that the pointer caught it.
- **Mouse support: click a chat to open it, click a pane to focus it, wheel to scroll.** Reported from the first live session — "мышкой невозможно нажимать". The state before this was worse than an unsupported mouse: `View` already set `MouseMode = MouseModeCellMotion`, so the terminal handed mouse events to lazytg and stopped doing its own text selection, while not a single handler existed — clicks did nothing *and* dragging to copy was broken, with the cost of mouse capture paid for no benefit. Click routing lives in `internal/ui/app/mouse.go` on top of a new `computeLayout` (`internal/ui/app/layout.go`) that resizing and hit-testing now share, because two copies of the same pane arithmetic is how a click ends up one column off. Row-to-chat mapping is `chats.ItemIndexAt`: the offsets it relies on are bubbles' own (a title/filter line is drawn even with `SetShowTitle(false)`, and the default delegate spans two rows plus one of spacing), so `TestItemIndexAt_MatchesRenderedRows` derives the expected rows from the *rendered* pane — a bubbles upgrade that adds or drops a line fails a test instead of silently selecting the wrong conversation. A click and Enter go through one path (`SelectAt` → `handleEnter` → `ChatSelectedMsg`); the wheel scrolls without moving focus, since scrolling to read is not the same act as choosing where to type; horizontal wheels are ignored rather than reinterpreted as vertical; the separator column, the status row, overlays and the too-small-terminal fallback are all inert. The thread's wheel reuses the keyboard's pagination decision (`paginateAfterScroll`), so scrolling up with the wheel keeps loading older history instead of stopping dead at the loaded window and reading as "no more messages".
- **The TUI now talks to Telegram.** `runTUI` connects before building the UI (`cmd/lazytg/cmd/attach.go`): it picks the account (`--account`, or the only logged-in one — several without a flag is an error rather than a guess), opens the stored session, builds the update dispatcher, runs `Client.Run` in the background and calls `App.AttachClient` once the session is confirmed authorised. Connecting first is deliberate: the composer and thread panes capture their dependencies at construction, so attaching afterwards would mean mutating fields the Bubble Tea goroutine already holds. Every failure path — no session, no network, revoked authorisation, 20 s timeout — degrades to the cached-only view instead of refusing to start, and logs the reason so `--debug` explains an empty list.
- History now loads when a chat is opened. `App.requestHistory` (`internal/ui/app/update.go`) asks `BackfillService` for the chat's history from all three paths that open one — row pick, palette pick, search jump. Before this, `Backfill.Enqueue` was called from nowhere in production and the thread pane never invoked its history provider, so a freshly synced chat opened empty and stayed empty: the list would fill in while every conversation in it read as blank. The request runs off the update loop (Enqueue blocks on a full queue, and the Bubble Tea loop must never wait on I/O) behind an 8-slot gate — Enqueue takes no context, so a stopped consumer would otherwise accumulate one permanently blocked goroutine per chat opened. Re-opening a chat re-requests only when the local mirror is behind the dialog list (see the freshness check below); it used to re-request unconditionally, which recovered messages that landed while the process was elsewhere at the cost of one `messages.getHistory` per visit.
- Chat list retrieval, which did not exist before: `internal/tg/dialogs.go` (`messages.getDialogs` with position-based paging, decoding users/basic groups/supergroups/channels and joining titles, usernames, unread counts, pinned flags and top-message dates) and `internal/core/sync/dialogs.go` (`DialogsService`, which persists chats *and their access hashes* and publishes `DialogUpdated`). Until now `SaveChat` was called only from tests — the `chats` table stayed empty in real use no matter how healthy the connection was, so the left pane had nothing to render. Peers are written before chats on purpose: the UI reacts to `DialogUpdated` by reloading and may ask for history immediately, which needs the access hash.
- Live updates reach the UI: `ClientConfig.UpdateHandler` lets the cmd layer install the dispatcher at construction (gotd accepts an update handler only there), and `AttachClient` now adopts a pre-installed `App.Updates` instead of replacing it with a second dispatcher that nothing feeds.

### Documentation

- **Install docs described a release that does not exist.** The Quickstart opened with `brew install kar43lov/lazytg/lazytg`, and `docs/INSTALL.md` listed `.deb`, `.rpm`, signed archives and `go install …@latest` as supported paths — while `git tag` is empty, `gh release list` is empty, repository secrets are unset and the tap repository `kar43lov/homebrew-lazytg` does not exist. Anyone handed the project followed the first instruction into a 404. Both documents now lead with the two paths that work today (build from source; run a binary someone built for you), each release-fed path carries an *available once the first release is tagged* note, and `docs/RELEASE_PROCESS.md` records which preparation steps are still undone so the claim and the reality stay attached.
- **Decision: releases ship without Telegram API credentials, and the docs now say so everywhere.** The pipeline has always been able to embed a pair through `-ldflags`, and the repository secrets that would feed it are deliberately left unset. A key inside a public binary is a published key — `strings lazytg | grep -E '^[0-9a-f]{32}$'` prints it without knowing what to look for (measured) — and Telegram blocks published `api_id`s permanently, for every user of that build at the same moment, the maintainer included; recovery needs a new application, which needs a new phone number, since each number carries exactly one `api_id`. Their own instruction is *"obtain your own API id before you publish your app"*. `docs/SECURITY.md` replaces its "shipped credentials: the accepted risk" section with the reasoning for the opposite choice, `docs/INSTALL.md` and `README.md` no longer promise credential-free release installs, and the Homebrew caveats spell out the two exports.
- **`release.yml` no longer fails a stable tag when the credential secrets are unset.** It treated that as a misconfiguration and aborted, which would have turned the very first `v0.1.0` red under the model the project actually chose. Unset now emits a notice and proceeds; exactly one of the pair set still fails the release, because a half-built embedded layer makes `ResolveCredentials` report "build-time credentials are malformed (report this)" — an alarming error about a defect the user cannot fix.
- **Docs that were quietly wrong about the current build, found while making the credential decision consistent.** `docs/CONFIGURATION.md` listed the credential layer as "embedded in releases" in both the env-var table and the precedence table; `docs/TROUBLESHOOTING.md` told users a release would carry a pair; `docs/INSTALL.md` had a whole subsection built around a "shipped key" that no longer exists, now rewritten as *Running on someone else's key* (what you take on when the binary you were handed carries someone's `api_id`). The release announcement draft claimed live updates run through `updates.Manager` — v0.1 does not wire it, which is exactly why the freshness guard needs its expiry — and described sessions as living in the OS keyring, which stopped being true when they moved into `secrets.age`. A stale link to a plan that had moved into `docs/plans/completed/` is fixed too.
- **New: what to do when `my.telegram.org` will not issue credentials** (`docs/INSTALL.md`). The form is unreachable from some regions — from Russia it commonly never delivers the login code or answers a bare `ERROR` — so "just register your own" is not advice everywhere. Documented: registering once over a VPN yields credentials that keep working from anywhere afterwards, since the pair belongs to the account and not the network; or receiving a pair, or a binary carrying one, from someone who has one, with the shared blast radius stated for both sides.
- **New: how to give a working build to someone else** (`README.md` → *Sharing a build*, `docs/INSTALL.md` → *Building for someone else* and *A binary someone built for you*). Cross-compilation targets verified by building all four (`linux`/`darwin` × `amd64`/`arm64`, ~21 MB, statically linked, no cgo); the credential decision spelled out with its trade-off — compiling a pair in means everyone running that binary shares one `api_id` with you, readable back out with `strings`, and a flag lands on all of them at once; and the macOS reality that a hand-delivered Go binary is ad-hoc signed, gets quarantined in transit and is refused by Gatekeeper until `xattr -d com.apple.quarantine` (verified: `codesign -dv` reports `adhoc, linker-signed`). `docs/TROUBLESHOOTING.md` gains that failure and the `Exec format error` architecture mismatch, both stated as symptom → diagnosis → fix.

### Fixed (found during the first live session)

- **Text disappeared as the pane separator moved.** Both panes were sized to the full width of the box they are drawn in, while the box spends one column per side on padding: every full-width row was two columns too wide, lipgloss wrapped the overflow onto a new line, each wrapped item grew from two rows to three, and the rows below were pushed out of the frame — the last chat simply vanished. The panes now subtract the padding, and the minimum pane width is the panes' own floor *plus* that padding: at exactly 20 columns the chats list clamped itself back up to its own 20-column minimum and re-created the overflow at the one width where it was hardest to see. `TestFrameNeverOverflowsItsWidth` asserts the frame is never taller than the terminal (lipgloss wraps rather than overflowing, so height is where this shows) and fails on the pre-fix code at three different splits; its first version passed against the defect because the fixture's chat titles were too short to overflow anything.
- **Messages you had just sent carried no time and no author.** They render from the optimistic-outgoing path, which produced bare text while every message around them showed `[HH:MM] name` — reported as "неудобно", and it is: the row reads as a different kind of thing until the server echo replaces it, which can be the whole session when live updates never deliver one. Optimistic rows now go through the same header renderer, labelled `you`, with the state glyph (⏳ / ✗) in the header rather than in front of the body so the text column does not shift. The send time survives the state transitions, which previously rebuilt the row from scratch — losing the timestamp at the exact moment the message was confirmed sent.
- **Senders were rendered as `user-8385473863`, including your own messages.** Names now resolve from the chat list (which covers the other party of every private chat and any group with its own dialog row), falling back to the 1:1 rule — in a private chat a sender who is not the peer is the reader, so it says `you` without an extra RPC or self-id plumbing — and only then to the numeric id, which is all storage has for group members (`peers` keeps ids and access hashes, no names). The directory is the loaded chat list, so a conversation opened by a search jump that never made it into the synced 500 still shows numeric ids.
- **The chat list showed names over blank rows.** The preview was never populated (`NewChatItem(c, "")`), so the pane looked half-drawn. `GetChats` now returns each chat's newest cached message text through a correlated subquery riding the existing `(chat_id, date DESC)` index — one statement, not a query per chat — and newlines are collapsed, because a multi-line preview would push every row below it down and break the mouse hit-test's row arithmetic. Chats whose history is not cached yet still show a blank line; filling those needs the dialog sync to persist the top message it already receives.

- **Message timestamps were rendered in UTC.** Every layer below the UI keeps time in UTC deliberately — storage, the tg mapping, search — and the renderer formatted that instant as-is, so a message sent at 19:32 MSK appeared as `[16:32]`: three hours in the past, which reads as a stale thread rather than a formatting bug. Fixed in `internal/ui/panes/thread/format.go` and `internal/ui/panes/search/view.go`. The golden fixtures moved to `time.Local`, because a UTC fixture would have made the goldens pass only on a UTC machine (CI) and fail on every developer's; `TestFormatHeader_RendersInLocalZone` pins the conversion with an explicit +03:00 zone.
- **The status bar said `connecting` forever.** `statusbar.New` starts in that state and nothing in v0.1 ever moved it: `events.ConnectionStateChanged` is published only by `ReconnectManager`, which runs on reconnect attempts, never on the initial attach. So a fully working session showed a yellow `connecting` for its whole run and an offline one claimed it was still trying — the indicator carried no information at all. The state is now seeded from the attach outcome (`initialConnState` in `cmd/lazytg/cmd/tui.go`, keyed on `runtime.Client`, which `AttachClient` and nothing else sets).
- **Re-opening a chat re-fetched its history over the network.** The UI enqueues a backfill on every chat selection and `BackfillService` only coalesces requests still in flight, so moving focus back and forth cost one `messages.getHistory` per visit — six calls for two chats inside 25 seconds in the smoke log, with every message already in SQLite. `HistoryService.LoadInitial` now asks the new `Repo.ChatHistoryFreshness` whether the mirror already holds the newest message the dialog list knows about, and skips the fetch when it does. Timestamps rather than a remembered "already loaded this chat": a chat that gains messages mid-run compares as stale and is fetched again, where a remembered set would have gone quiet until restart — precisely how a thread stops updating without saying so. Any probe failure falls through to fetching, because a cache check that cannot answer must never be the reason history goes missing. The verdict also expires after 90 seconds, and that bound is what keeps the guard honest: both timestamps it compares live in local storage, so a transport drop freezes them together and the comparison would keep answering «current» for the rest of the run — with no `updates.Manager` in v0.1, the messages missed during the drop would then stay invisible until the next restart. Expiry restores the accidental recovery the unconditional re-fetch used to provide, at one `getHistory` per chat per window instead of one per visit (`TestHistoryService_LoadInitial_RefetchesAfterFreshnessWindow`). Found by review, not by use.
- **`lazytg login` never said where the code was sent.** The prompt was a bare `Code from Telegram:` while `*tg.AuthSentCode` carries the delivery channel, and the natural assumption — an SMS — was wrong: the code had gone to the Telegram app on the account's other devices as a service message. That cost several minutes of searching and two extra `SendCode` calls, each one more behavioural trace from an unofficial client. The prompt now names the channel (app / SMS / voice or missed call, including the "code is the last N digits of the caller number" case / email / Fragment / "configure a login email first"), and adds Telegram's own fallback when it offers one: `[not arrived? resend switches to SMS, allowed after 60s]`.

### Fixed (found reviewing this change)

- `AttachClient` is called from the goroutine that goes on to build the UI, not from inside the gotd session callback. Cancelling a context does not interrupt code already running, so a handshake completing just after the 20 s deadline would have wired services onto `App` while the caller was already reading the offline values into the panes — a data race, plus a half-attached session whose dialog sync never started and whose log claimed "opening on local cache". Attaching on the success branch of the caller's `select` removes the window by construction rather than by a well-placed check. A ready signal arriving in the same instant as the deadline is now honoured instead of discarded (`select` picks randomly among ready cases).
- The dialog cursor is captured from a single dialog. It was assembled from separate sources — peer from the last decoded chat, message id from the last raw entry — which disagree whenever the final entry was skipped for missing metadata; Telegram answers an inconsistent position with skipped or repeated pages. A dialog whose top message is absent from the response now ends the walk instead of paging on `int(time.Time{}.Unix())` = `-62135596800`, which Telegram reads as "from the beginning" and which turned the walk into a re-fetch of page one. A cursor that fails to advance also ends the walk rather than spending the remaining page budget on identical requests.
- Session teardown waits (up to 2 s) for the session goroutine to unwind before the caller closes the database, and a session that ends mid-flight is logged — reconnect is still a stub, so the services stay bound to a dead client, and without that line the user sees sends failing with no stated cause.
- `NewBackfillService`'s error is logged instead of discarded, and the dialog walk states why it stopped: a page that came back full but carried no usable cursor means the list was truncated, which otherwise looks exactly like "these are all your chats".
- Dialog sync is bounded — 100 dialogs per call, 5 pages, 300 ms between pages. The cap and the spacing are ban-risk measures, not performance tuning: five back-to-back `getDialogs` calls in a few hundred milliseconds is not what a human opening an app looks like.
- Embedded API credentials for release binaries. `internal/tg.ResolveCredentials` picks credentials from three layers in descending precedence — `--api-id`/`--api-hash` flags, `LAZYTG_API_ID`/`LAZYTG_API_HASH` env vars, values injected at build time via `-ldflags` — so an installed release logs in without the user registering an application at my.telegram.org first. That step is a hard blocker in countries where the site is only reachable over a VPN and refuses application creation over one. A half-filled layer is an error rather than a silent fall-through to the next: believing you run on your own `api_id` while actually on the shipped one surfaces only as an unexplained ban. `lazytg version` gained an `api:` line reporting the active source (`flags`/`env`/`embedded`/`none`/`misconfigured: …`) and never the values.
- `internal/tg.ExplainCredentialError` turns Telegram's two `api_id`-level rejections into actionable text: `API_ID_PUBLISHED_FLOOD` (the key was found in public source and is refused permanently) and `API_ID_INVALID` (id and hash come from different applications). Both keep the original RPC error wrapped, so retry policies matching on the code are unaffected.
- `scripts/secret-scan.sh` — refuses any 32-hex string (the `api_hash` shape) outside the documented `0123456789abcdef…` placeholder. Wired as a lefthook `pre-commit` command (`--staged`, added lines only) and as the `secret-scan` CI job (`--all`, tracked files), the latter being the real gate since hooks are local, skippable, and absent for fork PRs. A published `api_id` is blocked by Telegram forever, and release binaries share one key, so a single leaked commit would break login for every release user at once.
- `Guard Telegram API credentials` step in `release.yml`, mirroring the existing Homebrew-token guard: a stable tag fails when both release secrets are empty, a prerelease only warns, and exactly one secret set fails on every tag type — a half-filled embedded layer builds a binary that greets the user with "build-time credentials are malformed (report this)", an alarming error about a defect they cannot fix. Without it an unset secret expands to an empty string, which is a perfectly valid `-ldflags` value — goreleaser succeeds, the release publishes, and every binary reports `api: none` while CI stays green from end to end.
- `scripts/secret-scan.sh --self-test`, run in CI before the scan itself. The gate leaked during its own review: the first pattern anchored on neighbouring non-hex characters, and since `grep -o` cannot restart a match on a character it already consumed, only the *first* hex run per line was ever reported. A line holding the documentation placeholder followed by a real key therefore surfaced only the placeholder, which the allowlist then dropped — the credential passed the gate silently. The pattern now matches `[0-9a-f]{32,}` and filters to exactly-32 afterwards (still rejecting sha1/sha256 digests), and the self-test pins that exact case. A scanner that quietly stops matching reports "clean" indistinguishably from one that found nothing, which is why the rules are now verified before their verdict is trusted. The same review found the scanner printing `clean` and exiting 0 when run outside a git repository at all — `git ls-files` failure was swallowed by the pipe — so both collectors now check git's exit status and abort with a distinct code instead. Staged scanning reports the filename (it previously printed a line number counted through the whole concatenated diff, pointing at nothing), CRLF files are no longer a blind spot, and the gate's known limits — obfuscated keys, uppercase hex, keys glued to longer hex runs, binaries, anything already on main — are documented in the script header and pinned by self-test cases.
- `scripts/secret-scan.sh --range <base>...HEAD`, run on every PR. A tree scan only sees the branch tip, which misses the likeliest real leak: a key committed, noticed, and deleted in a follow-up commit — tip clean, key still riding into main in the history, which is exactly what Telegram treats as published. Verified against a throwaway repository reproducing that sequence: `--all` passes, `--range` catches it. The CI checkout gained `fetch-depth: 0` so the base commit resolves. `scripts/` is now claimed in `.github/CODEOWNERS`, since a PR that weakens the gate is evaluated by CI in its already-weakened form and reviewer attention is the control that actually holds.

### Changed

- API credentials are no longer mandatory user setup. `docs/INSTALL.md`, `README.md` and `docs/CONFIGURATION.md` previously stated that lazytg "uses your own credentials, not a bundled key" and that both env vars are required; release binaries now ship with credentials embedded and only source builds need their own. The reasoning changed with the evidence: the risk of a shared `api_id` is a single shared blast radius (one block affects all release users, escapable by exporting your own pair), not extra per-account exposure — Telegram places accounts under observation for using *any* unofficial client, whoever owns the key.
- `CLAUDE.md` shrank from 241 to 120 lines by deleting what `docs/` already says verbatim — the stack table, the package tree, the FTS5 and release-pipeline sections and the `make` targets now live only in `docs/ARCHITECTURE.md`, `docs/SEARCH.md`, `docs/SECURITY.md`, `docs/RELEASE_PROCESS.md` and `docs/CONTRIBUTING.md`, with the roadmap moved to `README.md`. What replaced them is what could not be derived from the code: a routing table and a list of traps (the deliberately-uncompilable `sqlcipher` tag, the credential layers, the dialog-sync cap, why the session attaches before the UI is built, and both CI defects above). The file is loaded into every session for this repository and multiplied by every review subagent, so duplicated reference material there has an ongoing cost.
- `README.md` no longer claims that "the MTProto session attach in `runTUI` is still on the Stage 2 follow-up list — without it the TUI runs on the local SQLite cache only". That stopped being true when the attach landed; the Status section now describes what actually runs, including that no maintainer has yet exercised it against a live account.
- `docs/ARCHITECTURE.md` gained the dialog-sync section (positional paging, single-dialog cursor, non-advancing-cursor stop, and the 5-page cap as a ban-risk control rather than an unfinished loop) and its package map now lists `internal/tg/dialogs.go`, `cmd/lazytg/cmd/attach.go` and the dialog-sync service, all of which were missing.
- Release pipeline consumes two new repository secrets, `LAZYTG_RELEASE_API_ID` and `LAZYTG_RELEASE_API_HASH`. The names deliberately differ from the runtime env vars: a maintainer is likely to have `LAZYTG_API_ID`/`LAZYTG_API_HASH` exported in their own shell, and matching names would silently bake personal credentials into a public release. Unset secrets produce a working binary that asks for the env vars (`api: none`) rather than failing the build.

### Removed

- The `sqlcipher` build tag and its CI matrix axis. CGo SQLCipher integration is deferred past v0.1 — until then a stub silently using the unencrypted `modernc.org/sqlite` driver would have been a security misrepresentation.

### Fixed

- 🔴 **Sessions were never persisted on macOS, so the app could not work past a single process.** Found on the first live login. A gotd session blob is ~4.2 KB (auth key plus the full DC configuration), and `zalando/go-keyring`'s macOS backend builds a `security -i` command line that it refuses past 4096 bytes (`ErrSetDataTooBig`). The failure was anything but graceful: gotd calls `StoreSession` from inside connection setup, so the rejected write tore the connection down and the in-flight auth-status RPC failed with `engine forcibly closed: context canceled` — while `lazytg login` printed `logged in as …` regardless, because gotd's `Run` returned nil. Symptom for the user: login "succeeds", Telegram shows a new device, and every subsequent start opens on the local cache with a cryptic transport error in the log. Unit tests could not see it — they inject their own storage, and the keyring's limit only exists in the real backend. Secrets now live in `<config>/secrets.age` and the keyring holds only the passphrase that opens it, generated once so a desktop user is never prompted; headless boxes keep prompting as before. Verified end-to-end: the same handshake that used to die now saves a 4197-byte session and reads it back. Pinned by `TestSecretStore_HoldsSessionSizedValue`, `TestKeyringStore_RejectsSessionSizedValue` (which documents the limit that forced the design) and `TestKeyringPassphrase_GeneratesOnceAndReuses` (a provider that minted a new passphrase per call would be a silent logout). Cost: `age`'s scrypt adds ~390 ms to a session write and to the first read after start, against a 20 s attach budget. Because the store is a single ciphertext, every write rewrites every key — so writes now take an exclusive `flock` on a `secrets.age.lock` sidecar and re-read the file inside it, otherwise `lazytg login --account other` running next to a live TUI would silently drop the TUI's session on its next refresh (`TestAgeFileStore_ConcurrentProcessesKeepBothKeys`; the lock is a sidecar because the atomic rename swaps the data file's inode). A passphrase that no longer opens the file is refused rather than "recovered" — re-encrypting under it would destroy the only copy of the session (`TestAgeFileStore_WrongPassphraseIsNonDestructive`), so the error now names the remedy and `docs/TROUBLESHOOTING.md` documents it.
- **Concurrent writes were being lost.** No `busy_timeout` pragma was configured, and SQLite allows exactly one writer at a time: a connection that found the write lock taken failed its statement instantly with `SQLITE_BUSY` instead of waiting. lazytg writes from several paths at once by design — live drain, history backfill, dialog sync, FTS reindex — so this was not a rare race. Measured on a burst of 4 goroutines × 300 writes, **973 of the 1200 failed**. The user-visible symptom would have been messages that simply never appear, with a healthy disk and nothing in the log to explain it, and the first live smoke would have walked straight into it. `pragmaQuery` now sets `busy_timeout(5000)`; the same burst loses nothing. `TestConcurrentWriters_NoBusyFailures` reproduces the shape at 4 × 150 — smaller only to stay quick — and asserts zero failures. The timeout has room: the largest single write transaction in the app, a 5000-row `Indexer.Backfill`, was measured at 151 ms.
- **A write burst could put the whole repo into read-only mode.** `Repo.ProbeWrite` issues `BEGIN IMMEDIATE`, which needs the write lock, and `DegradationDetector` turns any probe error into soft read-only mode where every write returns `ErrReadOnly` until a later probe recovers. `SQLITE_BUSY` was treated as such an error — so a probe landing inside a write burst disabled all writes for up to the 30 s probe interval and told the user the filesystem was read-only. Contention is now reported as success, which is what it means: another connection holding the write lock is positive evidence that the storage accepts writes. No genuine failure code masks into that classification — `SQLITE_PERM` (3), `SQLITE_READONLY` (8), `SQLITE_IOERR` (10), `SQLITE_CORRUPT` (11), `SQLITE_FULL` (13), `SQLITE_CANTOPEN` (14) and `SQLITE_NOTADB` (26) each keep a low byte of their own — so degradation detection keeps whatever coverage it had. Pinned by `TestProbeWrite_ToleratesContention`, `TestProbeWrite_ReportsNonContentionFailure` and `TestIsContention_ClassifiesResultCodes` (the code table, including extended codes — the driver enables those on every connection, so masking is required rather than defensive). This surfaced as `Memory budget gate` failing on `main` with `seed corpus: save chat 7: repo: read-only mode`.
- Documented a **pre-existing gap found while reviewing the above**, rather than left implied: `ProbeWrite` cannot detect a read-only database at all. `BEGIN IMMEDIATE` takes the write lock but dirties no page, so SQLite never raises `SQLITE_READONLY` and the probe reports healthy storage while ordinary writes fail with "attempt to write a readonly database" — verified against the previous revision, where the probe returned `nil` just the same. `DegradationDetector` therefore misses the one condition it was written for, and the doc comment claimed the opposite. Corrected in the comment and in `docs/ARCHITECTURE.md`, and pinned by `TestProbeWrite_KnownGap_ReadOnlyDatabaseUndetected` — whose assertion is inverted, so it passes while the gap exists and fails the moment someone closes it. Not fixed here: the fix belongs with the detector, and `DELETE FROM chats WHERE 0` inside the probe transaction was measured to raise `SQLITE_READONLY` (8) while touching no rows.
- CI's `Lint` job never linted anything: it failed while installing the linter. `golangci-lint-action` and `golangci-lint` versions have to move together — `@v6` rejects any v2 outright and `@v9` requires `v2.1.0` or later, so the pinned `v2.0.2` could not run under either. Now `@v9` with `v2.12.1`, matching what developers run locally, because a skew there means CI and local disagree about findings. No local run reproduces this class of failure: locally the binary is already installed and there is no install step. The defect predated the first CI run — `ci.yml` triggers on `main` only, all work happened on a feature branch, so the workflow had never executed until the first PR merged.
- `TestReindex_GracefulCancel` failed on `ubuntu-latest` inside its fixture, not its assertion: `openTestRepo` caps every test's context at 10 s, and this test spends that budget seeding 10 000 rows under `-race` before `RunAll` is called at all (it died at chat 31 of 50). The deadline is now explicit — `openTestRepoWithBudget` — and this test takes 2 minutes for fixture plus assertions. The fixture keeps its size deliberately: the volume is what guarantees the 50 ms cancel lands while `RunAll` is still working rather than after it finished, which would reduce the test to a no-op that passes for the wrong reason.
- Search parser: a lowercase `key:value` token whose key did not match any known operator (e.g. `food:burger`) was silently dropped on its way out of `Parse`. The token now survives as plain free text — preserves URL-style and unknown-operator inputs verbatim.
- Search query builder: phrases containing a literal `"` produced `\"`-escaped MATCH expressions that FTS5 cannot parse. Switched to FTS5's doubled-quote escape (`""`).
- FTS5 live-write trigger now skips empty/NULL `messages.text` rows, matching `Indexer.Backfill`'s filter so service messages do not pollute the index.
- `TokenBucket.Wait` no longer leaks short-lived timers on ctx cancellation; switched from `time.After` to `time.NewTimer` + `Stop`.
- Send retry loop clamps FloodWait `retry_after` to a 1 s floor so a server (or buggy mock) returning 0 cannot spin the loop at the SendGuard ceiling.
- `progressThrottler` and `uploadProgressThrottler` now drop their per-id state on each transfer's terminal event — long-running TUI sessions no longer leak one map entry per completed file.
- Debug-bundle `goroutines.txt` no longer truncates at a fixed 1 MiB cap — the buffer doubles up to a 64 MiB safety bound so a busy app with thousands of goroutines does not silently lose frames mid-trace.
- Debug-bundle `db_stats.txt` rewrites the user's home prefix to `~` so the bundle does not leak the OS username via the absolute db path.
- `DBSizeMonitor` now sums the SQLite WAL/SHM side files into the threshold check — a heavy live-update session whose total footprint crosses 1 GiB no longer escapes the warning because the main `lazytg.db` file alone stayed under cap.
- Lazy reindex goroutine now recovers from panics and logs them at error level instead of vanishing silently — failures are still surfaced via bus events for normal errors, but a programmer mistake (nil deref, etc.) is no longer invisible.
- `TestDownloadService_Failure` glob now walks the actual store root instead of a fresh `t.TempDir()` — earlier the assertion was vacuous.
- Optimistic-UI flicker race: `applyOutgoingState{Pending}` is now a no-op so the bus event cannot insert an empty `[⏳]` row before `SendDispatchedMsg` (carrying the message body) lands.
- `SendFailedMsg` no longer clobbers a fresher draft or retargeted reply pointer when the user moved on while the failed send was in flight — the failure is dropped and surfaced as a warn log.
- Configurable `ScrollUp`/`ScrollDown` chords (default `ctrl+b`/`ctrl+f`) now actually scroll the thread viewport when the thread or chats pane is focused; previously the chord was advertised in `keymap.toml` and the help overlay but no code consumed it.
- `LiveService.persist` no longer republishes `DialogUpdated` onto its own subscription — the chats pane reacts to `MessageReceived` directly, which removes the buffer halving and the resulting potential for dropped events under burst.
- `?` (default `ToggleHelp` chord) no longer hijacks the input pane or the chats filter: when the input pane is focused or the chats list is in filter-input mode the keystroke falls through to the focused widget. Previously a question mark could not be typed into the message body or chat-list filter.
- Reply-preview truncation in the input pane is now rune-aware: a Cyrillic / CJK reply target longer than 50 codepoints is cut on a codepoint boundary instead of being byte-sliced mid-UTF-8. The byte-slice path emitted invalid UTF-8 to the terminal for the project's primary audience (Russian-speaking users).
- Optimistic row no longer disappears between `Sent` and the live echo: `applyOutgoingState{Sent}` flips the row's state in place (rendering as plain text without the `[⏳]` glyph) and `applyIncoming` removes it on the server-echo `MessageReceived`. Private 1:1 chats — where Telegram emits `UpdateShortSentMessage` instead of a follow-up `UpdateNewMessage` — therefore keep the user's message visible until manual reload.
- Inverted-race guard: a `SendDispatchedMsg` arriving after a terminal `Sent` or `Failed` bus event no longer re-creates a Pending row. The thread now records every finalised localID and short-circuits the late insert that would otherwise leave a phantom `[⏳]` no future event could resolve.
- Async send failures (FloodWait, validation, network retries exhausted) now restore the textarea body and reply pointer just like the synchronous-error path. The input pane stashes the dispatched body keyed by `LocalID` and reacts to `OutgoingMessageStateChanged{Failed}` on the bus; previously the CHANGELOG promise of "Failed sends restore the draft" only held when SendService returned an error before publishing — i.e. for the rare optimistic-store-write failure surface.
- Repeated `Ctrl-D` on the same media no longer spawns overlapping `DownloadService` goroutines that would race over the shared `<path>.partial` and corrupt the output. The app now reserves the `FileID` for the lifetime of the goroutine; a second chord while the first is in flight is a quiet no-op (debug-logged).
- Search overlay `Enter` now loads the matched message's ±5 context window via `search.Service.JumpContext` and scrolls the thread to the hit — even when the target message is older than the freshly-loaded initial-page slice. Previously the jump opened the chat at its newest 200 messages and the deferred `ScrollTo` silently no-op'd whenever the target was not in that window (the prime FTS5 use case for old hits). On a `JumpContext` error the path falls back to the legacy `OpenChat + deferred ScrollTo` so the user still lands in the chat.
- Search-jump no longer strands the user in an isolated ±5-message slice: the thread pane now exposes symmetric forward pagination (`Repository.GetMessagesAfter` + `applyPaginationNewer` + `AtBottom + hasNewer` trigger). Scroll-down at the bottom of the loaded window walks the model toward the present so messages newer than the window are reachable without re-opening the chat.
- Search-jump now resists stale repo loads: a slow `OpenChat` fetch (or in-flight older-page pagination) for the same chat can no longer clobber the freshly-installed jump window. The thread model carries a `loadGen` counter bumped on every `OpenChat` / `SwitchTo` / `LoadJumpWindow`; `loadCmd` / `paginateCmd` / `paginateNewerCmd` capture it at scheduling time and the matching apply-handlers drop messages whose generation no longer matches.

### Known gaps (Stage 2 + Stage 3 follow-up)

- Search overlay renders `chat=<id>` instead of the chat title — the overlay does not yet take a chat-title source. Cosmetic but UX-degrading on the killer feature.
- `from:@username` resolves through `chats.username` — a user whose row is not in `chats` (most group/channel senders) silently produces zero hits. Documented in `docs/SEARCH.md`; full fix needs a peer-username index.
- `in:#chatname` only accepts a single whitespace-bounded token, so multi-word chat titles cannot be expressed via the operator (`in:#general` works, `in:#"Family Group"` errors and `in:#Family Group` filters by `Family` only). Parser v0.1 splits tokens before applying operators; quoted-value-after-operator support is deferred to Stage 4+. Workaround: filter by `username` when the chat has one. Documented in `docs/SEARCH.md`.
- Reconnect, gap recovery and the polling fallback are wired but have never faced a real outage. They are covered by unit tests and by steps 13–14 of `docs/MANUAL_SMOKE.md`, and that smoke has not been run — everything about them is asserted against fakes.
- Foreign-key cascade (`messages.chat_id REFERENCES chats(id)`): `LiveService.persist` still does not upsert a chat row, so a message from a chat outside the synced page window has no parent row. `DialogsService` covers the first 500 dialogs, which makes this rare rather than fixed.
- Dialog sync stops after 5 pages (500 chats) by design — an unbounded crawl is the access pattern the ban-risk policy avoids. Accounts past that see their remaining chats only once those chats receive a message.
