## [Unreleased]

### Added

- **Messages can be acted on, one at a time or several at once.** The client could read and reply and nothing else: a typo stayed a typo, a message sent to the wrong chat stayed there, and copying meant selecting with the mouse. `Space` marks the message at the cursor and marks accumulate, `y` copies, `e` rewrites your own, `d` deletes. Everything acts on the marked set when there is one and on the cursor when there is not, which is what makes the batch worth having — mark four messages and one `d` removes all four. Three details are deliberate. Deleting asks first, and asks the right question: for a chat where Telegram allows it the choice is "delete for everyone" or "just for me", and for a channel it is neither, because there the message is simply gone. Editing refuses somebody else's message locally rather than letting the server refuse it, so the answer is instant and the draft is never lost — the composer stashes what was being typed and puts it back on `Esc`. And the delete request picks its RPC by peer kind: a channel numbers its messages from one, so `channels.deleteMessages` and `messages.deleteMessages` take ids from different spaces and the wrong one deletes a stranger's message with the same number.

- **The account's Telegram folders, as tabs over the chat list.** People who use folders on their phone have already done the work of sorting their conversations; the client ignored it and showed one flat list. `[` and `]` walk the strip, `All` is always first, and the filter runs over the chats already loaded — no extra request per switch. Folders are read once at connect (`messages.getDialogFilters`) and matched by the same rules Telegram applies: explicit excludes win over explicit includes, then pinned, then the category flags (contacts, non-contacts, groups, channels, bots), and `exclude_read` last. A chat-list folder — the shared kind you join by link — carries no category flags at all, so it is matched by its explicit membership only; treating its empty flags as "everything" would have made it a second `All`.

- **Following a reply back to what it answers.** A reply quotes one line of the message it answers, which is enough to recognise it and never enough to read it; every graphical client makes that quote clickable for exactly this reason. `p` goes to the parent of the message at the cursor and `Ctrl+O` comes back, a pair that behaves like an editor's jumplist because that is the model this program's audience already has. The fast path is local — a reply usually sits a few messages below what it answers, so the parent is already rendered and the jump is a cursor move with no I/O — and when it is not, the same window loader the search jump uses fetches it from the mirror. The trail is capped and dropped on a chat switch, since every entry names a message in the conversation being left.

- **"typing…", for the chat you are reading.** It costs nothing to receive — the server pushes these whether or not a client looks — and it is most of what separates a conversation from a mailbox. Telegram's own vocabulary is kept rather than flattened to "typing", because the difference changes what the reader should do: "recording a voice message…" means wait, "sending a photo…" means something is on its way. Two things make it behave. It expires on a timer rather than on Telegram's "stopped" notification, which is sent only sometimes — a client that waited for it would leave somebody typing forever — and one sweep runs at a time, so a busy group does not multiply its own timers. It is shown only for the chat on screen: activity in a conversation the user is not reading is a distraction, and the chat list already moves when something actually arrives. Several people at once are counted rather than named, because in a busy group the names take the whole line and change every second. 🔴 Nothing is sent in the other direction: announcing this account's own typing would be a request every few seconds for as long as somebody is writing, on an account already under observation for running an unofficial client.

- **Reactions, read and sent.** A reaction is the cheapest thing two people can say to each other on Telegram — an acknowledgement that costs neither of them a notification — and a client without them presents a conversation with half the replies removed. They now render under the message with counts, the one this account sent boxed so the next keypress is predictable, and a count of one left off because the emoji already says one person did it. `r` opens the emoji picker for the message at the cursor; picking what is already there takes it back, which is the same request with nothing in it, because that is how the protocol expresses removal. Deliberately the cursor rather than the marked set: reacting to five messages with one emoji is not an ordinary thing to want, and it would be five requests on an account already watched for running an unofficial client. The new counts come from the server's own answer rather than from incrementing the local copy — counts belong to everybody, and a client doing its own arithmetic drifts the moment two people react at once; when the response says nothing, nothing is announced and the push update fills it in. Migration `0012` stores them as JSON in one column rather than in a table of its own: the thread reads messages a page at a time and renders each row whole, so a side table would put a join on the one query whose latency the reader feels, to normalise a list nothing ever queries across messages. Premium custom reactions are skipped — they are a document id rather than a character, so showing one means downloading and drawing a sticker, and a count attached to nothing is worse than the reaction being absent.

- **Forwarding, on the cursor or on a marked set.** `f` asks which chat and sends what was marked. Naming the messages and naming the destination are two separate acts on purpose: doing both on one keypress is how a message ends up in the wrong conversation. The chat is picked in the command palette rather than in a new widget — it already lists every chat, ranks by frecency and matches Unicode-fuzzily, and a second chat-picker would be the same list with different keys — so the palette gained a purpose rather than a twin, and what Enter does there depends on why it was opened. Picking the chat the messages came from is refused, because it is top of the frecency list and therefore the easiest mistake to make. Nothing is written locally and nothing is announced: the forwarded copies are new messages in the target chat and arrive through the live update path like any others, so storing them here would produce a second copy the moment the update landed. Each message gets its own random id — Telegram deduplicates sends by it, and reusing one silently drops the second copy of a forward.

- **Emoji, without reaching for a mouse or another window.** Two ways in, because they answer different questions. Someone who knows what they want types `:rocket` and presses Tab; pressing it again walks the other matches, so a wrong first guess costs one keystroke rather than a deleted word. The gesture is deliberately readline-shaped rather than a popup with its own keys — no mode to enter, no mode to leave — and Tab only reaches the composer when there is a shortcode under the cursor, so it still cycles focus the rest of the time. A colon that does not open a word is left alone: a client that eats the time in `10:30` is worse than one with no completion. Someone who would recognise what they want on sight opens the picker with `Alt+E`, where typing filters, `[`/`]` walk the categories, and what was picked this session comes back first. The table itself is generated from the Unicode data rather than hand-written, because a hand-written list drifts from the official names and stops wherever its author lost interest; a short alias table on top carries the shortcodes people actually type, since nobody writes `:face_with_tears_of_joy:`.

- **Photos drawn inside the thread.** A badge answers "there is a picture here", which is not the same as answering "what is in it", and for a photo that is most of the message. `i` draws it in terminals that speak the Kitty graphics protocol — Ghostty, kitty, WezTerm — and leaves the badge alone everywhere else. Not sixel: 256 colours, no transparency, and an encoding several times fatter on the wire than the PNG. Detection reads the environment rather than querying the terminal, because a query is a round trip on a link that may be `ssh` and a slow answer is indistinguishable from no answer; inside `tmux` or `screen` the answer is always "cannot", since the multiplexer hides the outer terminal and does not forward graphics escapes — `LAZYTG_IMAGE_PROTOCOL=kitty` overrides that for a passthrough setup, `=none` turns drawing off entirely. Nothing is drawn unasked: a thread that fetched every photo it scrolled past would be slow, would spend the user's bandwidth, and would produce a request pattern no ordinary client does. The picture takes the thread's width and at most half its height, because filling the pane leaves the user looking at one photo with no idea what was said around it. Photos only — a video's first frame needs a decoder this client does not have, and `o` still hands anything to the system viewer, which for video is not a fallback but the whole answer.

- **`i` had to be built against the fact that a picture is not part of the text grid.** The terminal anchors it where the escape was written, and repainting those cells with spaces does not remove it. So every image carries an id derived from its message id and its escape opens by deleting that id's own placements — without which a thread that scrolls (or merely repaints a line when the cursor moves) leaves a copy behind and the photo multiplies down the pane. Closing one picture sends the delete for its id, switching chats sends the delete for all of them, and both go out through `tea.Raw` rather than through a frame, because a frame can only paint cells. `q=2` on every sequence stops the terminal acknowledging each draw back up stdin, where the TUI's input parser would have to swallow it.

## [0.1.0-alpha.2] - 2026-09-04

Everything below came out of live runs against a real account rather than out of the test suite — two ordinary sessions, one over attachments, and the security pass that followed. The pattern is now consistent enough to state plainly: coverage in `core` sits around 81% and catches logic, but not what happens between the process and the server, and least of all what happens when a fixture fills in a field the server never sends.

### Known gaps opened in this release

- **An empty thread has three different causes and the client tells them apart for nobody.** A chat opened on 04.09.2026 showed no messages at all. It can mean the conversation is genuinely empty, that it holds only service messages, or that backfill never ran — and none of the three is visible from the outside. `decodeHistory` (`internal/tg/history.go:87`) keeps only `*tg.Message`, dropping `MessageService` and `MessageEmpty` silently, so a chat of "X joined the group" rows decodes to zero messages and looks identical to an empty one. Meanwhile `HistoryService.LoadInitial` logs `history: empty batch` at `Debug` (`internal/core/sync/history.go:120`) while the app runs at `Info`, so the log does not separate "the server returned nothing" from "we never asked". Fixing it means two things that belong together: render service messages instead of discarding them, and raise that line so an empty result is on the record.
- **Types the platform opens without an execute bit are not filtered.** `o` hands the attachment to the system viewer, and `.webloc`, `.inetloc`, `.url`, `.terminal` and `.html` behave exactly as they would from Finder. The executable kinds are already blocked by the file mode (`0600`, no `+x`) and the badge can no longer disguise an extension, so what remains is the same exposure as opening the attachment from any other client. A deny-list is the next step if that judgement changes — see `docs/SECURITY.md`.
- Neither of the two large batches merged in this release (PR #24, #33) nor the security fix (PR #34) had an independent review: both third-party engines were out of quota on 19.08 and again on 04.09. Everything here carries one signature.

The older list, unchanged, is under `0.1.0-alpha.1` → **Known gaps**.

### Added

- **A cursor over messages, and a way to look at what is attached to them.** The thread had no notion of "the message the user means": reply armed the newest message and Ctrl-D took the newest attachment, both pinned as interim UX. That works until somebody sends two photos in a row, at which point the first one is unreachable — there was no gesture in the client that could name it. `↑`/`↓` (and `k`/`j`) now move a cursor over messages, a click puts it where the pointer is, and reply and download both act on it. The cursor is a message id rather than a row: live messages arrive, older pages load above, deletions from another device remove rows, and an index would keep pointing at the same position while the message under it changed — the same defect the chat list had. An untouched cursor resolves to the newest message, so nothing about the old behaviour moved for a user who never presses an arrow key.
- **`o` opens an attachment in the system viewer; a click on its badge does the same.** It downloads first if the file is not already on disk, which is free when it is — the dedup cache answers without touching the network. `open` on macOS, `xdg-open` elsewhere, overridable with `LAZYTG_OPEN_CMD` (`"mpv --loop"` plays a round video message the way Telegram does). The viewer is executed directly rather than through a shell, because its argument is a filename chosen by whoever sent the message; the path must be absolute and must exist, so a leading dash cannot be read as a flag; and it inherits none of the TUI's streams, so it cannot paint over the thread or eat keystrokes. This is also the honest answer for video: a photo could one day be drawn inline through a terminal graphics protocol, but no terminal plays a video, so handing it to something that does is the whole feature rather than a fallback. Without a viewer wired the gesture degrades to a plain download.
- **Attachments say what they are.** Everything that was not a photo used to be a "document" — true of the MTProto wire and useless to a reader, because a voice message, a round video message, a sticker and a PDF all rendered as the same grey badge. Worse, Telegram sends no filename for exactly the kinds people meet most often, so a video note read `[📎 document_5123.bin]`. The converter now reads the document attributes it was already receiving: `DocumentAttributeVideo.RoundMessage` is the one bit separating a кружочек from an ordinary video, `DocumentAttributeAudio.Voice` separates a voice message from a music track, and an animated flag alongside a video attribute means a GIF rather than a video. Migration `0011` stores the duration, so the badge reads `[⏺ video note, 0:07, 1.2 MiB]` — enough to decide whether to spend the download. The migration does not rewrite rows written earlier — but opening the chat does, because the ordinary backfill re-fetches history and runs it back through the converter, so attachments stored before this change appeared as video notes on the first live run without anything special being done. The download path deliberately does not switch on the kind — a photo is a photo and everything else is a document — so adding a kind cannot silently stop it downloading.

- **The composer grows with the message, up to four rows.** It was a single row, with `$EDITOR` as the escape hatch for anything longer — which reads as broken the moment you write two sentences, because the beginning of what you are typing scrolls out of sight one line at a time and there is no way to look at it. It now grows as the text wraps and shrinks back when the draft is sent or deleted; the panes above give up rows and take them back, so the frame still fits the terminal. Four is the ceiling: past that the text scrolls inside the box, and a genuinely long message still belongs in `$EDITOR` via `Ctrl-E`.

- **The composer was two columns wider than the box it is drawn in.** `SetWidth` was handed the full terminal width while `inputStyle` spends two columns on padding, so every line long enough to reach the edge was wrapped by lipgloss into two. Invisible while the composer was one short row, and immediately visible when it grew: three rows of text rendered as six and pushed the frame three rows past the bottom of a 24-row terminal. Found by the test that asserts the frame fits, which is the only reason it was not shipped.

- **A rule between days in the thread.** The pane printed times and only times, which is right inside one day and misleading across days: the same live run showed `16:35` directly above `15:10` and read as a broken sort, when in fact a fortnight separated them. Each change of local day now draws `─── August 19 ───`, with the two most recent days named rather than dated (`Today`, `Yesterday`) and the year shown only when it is not the current one. The separator belongs to no message, so a click on it selects nothing. It also broke three mouse tests on the way in — they addressed rows by hard-coded number, so two extra lines at the top of the thread failed them while the gesture they cover kept working; they locate their row by content now.

### Changed

- **`↑`/`↓` (and `k`/`j`) in the thread now move the message cursor instead of scrolling by a line.** The pane's unit is a message, not a row: everything the user does there names one. Covering distance is still the page keys' job — `PgUp`/`PgDn`, the configurable `Ctrl-B`/`Ctrl-F`, and the wheel — and the cursor scrolls the minimum needed to stay visible rather than re-centring on every press. A message taller than the window shows its head, which is where the author and the attachment badge are.

### Security

- **Text written by somebody else was drawn straight into the terminal.** Every string lazytg renders from Telegram — a message body, a chat title, an author label, a search snippet, and now an attachment filename — is chosen by whoever sent it, and none of them were filtered. The terminal reads escape sequences as commands, so the consequences are not cosmetic: lazytg copies to the clipboard with OSC 52, which proves the terminal it runs in honours OSC, and a filename carrying an OSC 52 sequence would have rewritten the user's clipboard the moment the message scrolled into view. The same class covers OSC 8 (a hyperlink whose visible text and target disagree), CSI (repaint the pane, hide a line, move the cursor) and the bidi overrides, which reverse display order so an attachment named `.command` is drawn as `.png` — in a client where the next keypress hands that file to the system viewer. `internal/ui/safetext` now strips C0, DEL, C1 and the bidi controls at render time, in the thread, the chat list and the search overlay. Three things it deliberately does not do: it keeps the zero-width joiner, because emoji and several scripts are built with it and it cannot steer a terminal; it keeps newlines and tabs where the pane lays them out itself; and it runs on the way to the screen rather than into storage, so rows written before it existed are covered too and the search index keeps matching what the sender actually wrote. Found by the security pass over the media work, not by a report.

### Fixed

- **A reply that arrived live had no parent.** `events.MessageReceived` carried no reply pointer, so the converter's answer was thrown away between the wire and the pane: a reply that came in while the chat was open rendered without its quoted line and stayed that way until the chat was reopened and the row came back from storage. It went unnoticed because every test fixture built the message directly rather than through the event — the same shape of defect as the `from_id` one, and found the same way, by a feature that needed the field and got a zero. The pointer now rides on the event, along with any reactions the message already carries, and the converter's reply-header walk is one function both paths call.

- **The cursor stayed behind on a jump.** Landing on a message scrolled it into view without putting the cursor on it, so the next keypress — download, reply, react, follow the reply — acted on wherever the cursor had been left, possibly off screen. It also made following a chain of replies impossible, because the second press had nothing to work from.

- **Two attachments with the same name overwrote each other, and the cache then served the wrong bytes.** Telegram does not ask the sender for a filename: every video shot on a phone arrives as `video.mp4`. The on-disk path was `<root>/<chat>/<filename>` with nothing making it unique, so a second such video wrote over the first — and because the dedup cache is keyed by file id, the older id was left pointing at a file that now held somebody else's video, which it would happily hand back on the next Ctrl-D. Found by reading a real mirror rather than by a report: eight attachments in it, every one named `video.mp4`. `FileStore.Reserve` now picks a free name browser-style (`video (2).mp4`) and claims it by creating the `.partial` with `O_EXCL`, which also closes the narrower race the old code had — two downloads starting in the same instant both truncating one temporary file. A stale `.partial` from a killed process costs one suffix rather than a truncation of bytes another process may still be writing.

- **Every message in a private chat was labelled `system`, and the label changed under the user.** Telegram omits `from_id` in a 1:1 dialog — the sender follows from the `out` flag and the peer, so the field carries nothing and the wire format leaves it out — but both converters read it and nothing else, so private messages reached storage with sender 0, which the thread pane renders as a service message. It was intermittent in a way that made no sense from the outside: a live update sometimes arrives in the short form, where gotd fills `from_id` in, so a new message showed the sender's name until the next open of the chat pulled the same message through `messages.getHistory` and overwrote the row with NULL. Seen live on 19.08.2026 — four messages in one conversation, three of them silently relabelled between two screenshots. Migration `0010` stores the direction, both converters derive the sender (incoming private messages are attributed to the peer; outgoing ones are identified by direction rather than by an id, which would need a self-id lookup plumbed through every constructor), and `resolveAuthor` labels an outgoing message `you` before it looks at any id. The existing test suite could not have caught this: its fixture set `from_id` explicitly, which is the one thing Telegram does not do here.

- **A message arriving in a chat you were not reading showed nothing at all.** `unread_count` was written only by dialog sync, which runs at startup, so a new message moved the chat up the list and left no badge — the count appeared hours later, or after a restart. `LiveService` now raises it as the message is stored, skipping two cases that would show unread for something already read: the chat currently open, and the user's own messages arriving from another device. The chat pane picks the new count up through the reload it already runs on `MessageReceived`, so no extra event crosses the bus.

- **A conversation read live stayed unread on every other device.** `ReadService` acknowledged the open and nothing after it, so a chat the user was reading in real time kept climbing the badge on their phone for as long as the exchange lasted. Messages arriving into the open chat are now acknowledged as they land, naming the arriving message rather than looking the newest one up — the live save is a separate subscriber on the same event, and reading storage here races it. The two kinds of acknowledgement have separate queues, because they behave differently under load: an open is a discrete user action and each one matters, while acknowledgements of arriving messages supersede one another, so only the newest is worth keeping. Sharing one queue would spend a request per message and let a busy conversation push another chat's open off the end. This closes a gap that had been documented as needing UI state the core cannot see; it needs nothing of the sort — the chat that was opened last is the chat that is open.

- **The cursor in the chat list silently moved to a different chat.** Selection was preserved by index, and the list is sorted by last-message date: an incoming message promotes its chat to the top and shifts every row below it down, so the highlight stayed on row 0 and came to point at a conversation the user never picked. It reads as a bug in the thread pane rather than the list — the highlighted chat is not the one whose messages are shown, which is exactly how it was reported after the 19.08.2026 run ("opened the chat, the thread is empty"). The cursor now follows the chat id across a reload, falling back to the index when that chat is gone, which lands on the row that took its place.

- **A chat discovered live kept a placeholder name until the next launch.** `EnsureChat` creates the row from what an update carries — an id and a peer kind — and nothing asked the server for the rest, because dialog sync runs at startup. So a conversation that began while lazytg was open showed as `chat 275641346` in the list and as the sender's name in the thread, indefinitely. `EnsureChat` now reports whether it created the row, `LiveService` announces that as `ChatDiscovered`, and `Rediscoverer` turns it into one dialog sync — which brings the title, the username and the unread count. The refresh is on a 30-second cooldown: a new conversation is a human-paced event, but being added to several chats at once is not, and one `getDialogs` per message would be a request pattern no ordinary client produces. The sync runs on its own goroutine rather than in the bus read loop: `events.Bus.Publish` drops events aimed at a subscriber whose buffer is full, and a dialog walk holds its goroutine for seconds while it paces between pages — long enough for ordinary traffic to fill the buffer and push the *next* discovery off the end.

- **Reading a chat here left it unread everywhere else.** `messages.readHistory` was never called — not debounced, not deferred, absent — so a conversation opened in lazytg kept its badge on the phone and the desktop, and the local counter only ever moved when dialog sync happened to refresh it. `ReadService` now acknowledges the chat the user opens, then clears the local counter and announces the change. It stays quiet on the wire: a chat whose newest message has already been acknowledged this session costs nothing, and a chat with no messages is skipped, so what reaches Telegram is one request per conversation the user actually opens with something new in it. A server that refuses leaves the badge alone — a chat shown as read while the server still holds it unread is the one outcome worse than a stale badge, because nothing on screen says so. Reading without ever acknowledging is also a behavioural pattern no ordinary client produces, on an account already under observation for being unofficial. The request itself runs off the bus read loop for the same reason the dialog refresh does — a subscriber that stops reading to wait for a server has its buffer filled by ordinary traffic, and the next `ChatOpened` is dropped silently, leaving the chat the user is looking at unread.

- **Deleting a message on another device did not delete it here.** `updateDeleteMessages` and `updateDeleteChannelMessages` fell into the dispatcher's "unhandled type" branch, so the mirror kept every message the server had dropped — including the search index, which happily returned them. They are handled now: the rows go, the open thread drops them, and the chat list reloads. The subtlety worth naming is the id space: for private chats and basic groups Telegram sends message ids with no chat, because those ids are unique across that whole space for one account — but a channel numbers its own messages from one, so id 42 exists in both places and means different things. Both the storage delete and the thread pane filter by chat kind rather than matching bare ids, and each has a test that fails by deleting somebody else's message.

- **Deleting a chat on another device did not delete it here either.** Dialog sync only ever upserted, so a chat removed elsewhere stayed in the list for good — observed live on 19.08.2026, where the sync reported one chat fewer in the same breath as the list kept showing it. The sync now prunes chats the server stopped listing, and their messages follow through the cascade. 🔴 It prunes only when the walk reached the end of the dialog list on its own: the walk stops after five pages by design, and for an account past 500 chats "absent from the pages I fetched" is the normal state of most chats, so pruning there would delete the larger part of the mirror on every sync. An empty dialog page is likewise not treated as "no chats any more" — one bad answer from the server would otherwise erase everything.

- **Gap recovery never ran, on any account, since it was wired.** The `state` and `channel_state` tables named their key column `account_id` and declared it `REFERENCES accounts(id)` — but gotd's `updates.StateStorage` is keyed by the Telegram user id, and `accounts.id` is a local rowid (`1` on a first login). The two identifier spaces cannot coincide, so every `SetState` failed with `FOREIGN KEY constraint failed (787)`, `updates.Manager` refused to start, and the client ran with no gap recovery at all while logging one warning per launch. Migration `0009` rebuilds both tables keyed by the Telegram user id and without the foreign key, which is the same scoping rule `channelAccessHasher` already documents: accounts are separated by data directory, so one database holds one account's state. Verified against a real database: the pre-migration insert fails with 787, the post-migration one succeeds, and `PRAGMA foreign_key_check` and `integrity_check` come back clean with all rows intact. The unit tests missed this for the same reason every time — they seeded an accounts row whose id equalled the user id they then passed in; `TestStateRepo_AcceptsATelegramUserID` now uses a realistic pair and fails with the exact production error when the fix is removed. Found by the first live smoke that watched the log.

- **A message from an unknown chat was dropped and the chat stayed invisible until a restart.** `messages.chat_id` references `chats(id)` and the live path never created the parent row, so the first message from a new contact hit the same foreign key and was lost: `live: save message failed … FOREIGN KEY constraint failed (787)`. The chat itself only appeared after a restart ran dialog sync. `events.MessageReceived` now carries the peer kind the dispatcher already decodes, and `LiveService.persist` calls `Repo.EnsureChat` before saving — an `ON CONFLICT DO NOTHING` insert that creates a bare row and never touches an existing title, so dialog sync still owns the name. Until it does, the chat list shows `chat <id>` rather than a blank row. Two rough edges are accepted rather than hidden: the row carries `unread_count = 0` because an update does not report a chat's unread total, so a live-discovered chat shows no unread badge until sync runs; and a broadcast channel is recorded as a supergroup, because both arrive in the same peer container and guessing supergroup keeps the chat in the list people actually read. `EnsureChat` checks for the row with a read before it writes — this runs once per incoming message, and taking the write lock only to discover there is nothing to do would double the write-lock traffic on the busiest path in the client. This was listed as a known gap on the theory that it needed a chat outside the synced 500-dialog window; the live case is far more ordinary than that — anyone messaging you for the first time.

- **The thread rendered live messages in arrival order rather than by date.** `applyIncoming` appended unconditionally, which is correct only while one producer exists; since Stage 4 the live path and the polling fallback both publish `MessageReceived` and race, so a reconnect delivers its backlog through whichever wins. Two messages sent a second apart during a real outage came back swapped. Insertion is now by `(Date, ID)`, scanning from the tail so the ordinary case stays an append. The id breaks ties because Telegram stamps whole seconds.

- **An outage left no trace in the log.** `ReconnectManager` logs its own attempts, but those only happen when a session actually dies; gotd reconnects inside its own `Run` loop first, and the transport-state transitions that record it were logged at `Debug` while the app runs at `Info`. The result: the status bar went offline and back while the log file stayed empty, and nothing about the outage could be reconstructed afterwards. Transitions are `Info` now — repeats were already suppressed, so it is one line per real change of state.

- **The degradation detector could not see the condition it exists for.** `Repo.ProbeWrite` ran `BEGIN IMMEDIATE; ROLLBACK`, which takes the write lock but dirties no page — so SQLite never raised `SQLITE_READONLY`, and a database the process could read but not write was reported as healthy storage while every `SaveChat` failed with "attempt to write a readonly database" (8). `DegradationDetector` stayed in rw mode, the status bar said `rw`, and writes kept failing. The probe transaction now also runs `DELETE FROM chats WHERE 0`: the predicate is constant-false so no row can ever be removed, but the statement still opens a write cursor, which is the moment SQLite refuses. The gap had been documented rather than fixed, with `TestProbeWrite_KnownGap_ReadOnlyDatabaseUndetected` asserting it inverted so that closing it would fail the suite; that test is replaced by `TestProbeWrite_DetectsAReadOnlyDatabase`, which asserts detection against a real `mode=ro` file and first checks that the fixture still rejects an ordinary write, plus `TestProbeWrite_LeavesNoRowsBehind` — a probe that deletes has to be proven not to delete. Contention tolerance is unaffected: `BEGIN IMMEDIATE` fails first under a held lock, and the probe still returns nil there (`TestProbeWrite_ToleratesContention`).

- **A dropped connection ended the session for good.** `ReconnectManager` was built by `AttachClient` and started by nobody: `Run` had no caller in production, so the state machine that owns offline → connecting → online never ran. Underneath it, `reconnectAdapter.Connect` returned `nil` without doing anything, so even when the manager did run it was told a dead session had been repaired. The combination cost more than reconnection: `ReconnectManager` is the only publisher of `events.ConnectionStateChanged`, so the status indicator never moved after the seed value the initial attach wrote — the green "online" survived pulling the network cable. Now the MTProto run loop lives in a supervisor (`cmd/lazytg/cmd/session.go`) that can stand a fresh session up, `Connect` delegates to it, and the manager runs for the lifetime of the session. An adapter with no supervisor behind it returns an error rather than `nil`, because a manager that believes it reconnected publishes "online" over a session that is gone — the one outcome worse than staying offline.
- **Two defects the reconnect work created, both found in review and both fatal to it.** First: gotd's `telegram.Client` is single-use — `Run` cancels the client context on the way out, so a second `Run` returns `client already closed` without sending a packet. A supervisor that restarts sessions on one gotd client would have failed every attempt forever and reported it as a network problem. The client is now rotated per session, with `Client.API()` kept as one fixed object over a swappable invoker: services capture it at attach and the panes capture those services at construction, so replacing the object underneath them would be a data race against the Bubble Tea goroutine. Second: standing a new session up tears the old one down, and that teardown reports itself on the same disconnect channel the manager is about to read again. `context.Canceled` reads as user-initiated shutdown, so the manager returned after its first successful reconnect and recovery worked exactly once per process; a teardown carrying a plain error instead sent it into a cycle of tearing down the session it had just recovered — measured at 1.27 million reconnect attempts in 200 ms against fakes, which on a real account is a login storm on a client Telegram already watches. Both are pinned by tests that fail with exactly those symptoms when the fix is removed. A fourth, and the one that mattered most for ban-risk: a teardown that did not finish inside the grace period was a warn line and nothing else, so `Restart` went on to open a new session while the old run loop still held a connection. Two run loops on one account are two devices logging in, on a client Telegram already watches for being unofficial, and a flapping link produces the situation over and over. Restart now refuses, with a retryable error, so the manager waits the old session out instead. A third, found by the third review engine: the gap-recovery goroutine was cancelled but never joined, while the update manager is shared across sessions — so the next session could reset the manager's state while the previous run's goroutines were still writing pts to the same rows. The session is not considered gone until that goroutine has returned.
- **The connection indicator only ever knew what lazytg did, not what the connection did.** gotd reconnects on its own while `Run` is executing, and it never returned in that case, so an entire outage was invisible. gotd 0.161's `OnConnectionState` closes that: `tg.Client` now exposes a one-slot state feed (latest wins — the callback runs synchronously on gotd's connection path and must not block), `ReconnectManager` pumps it onto the bus for as long as it runs, and repeats are suppressed so a flapping link does not wake every bus subscriber per event.
- **`--polling` did nothing.** The flag was parsed, stored in `app.Config` and read by no one, so a user who reached for it *because* live updates were not arriving got exactly the behaviour they were working around, silently. It now starts the fallback that has existed since Stage 2: the three most recently active chats, polled every three seconds, publishing only what is newer than what the mirror already holds. It runs alongside the push path rather than replacing it — the flag's own description said "instead of updates.Manager", which was never the useful behaviour. Three chats at three seconds is one request per second, and the cap is a ban-risk decision rather than a throughput one. The fallback's watermark now takes the higher of its own and the store's, so messages the live path already delivered are not republished on the next tick. Failures are logged as a streak rather than per tick: every poll fails for every polled chat while the connection is down, and one warn each is sixty lines a minute — enough to rotate the log file and carry off the diagnostics that explain the outage. And polling now publishes through the same duplicate filter the live path uses, which is the only thing that can close the overlap between them: the source reads the store's newest id, then the poll makes a network call, and a live update landing in that window is newer than the watermark the call went out with — so the message would be shown twice. One filter across both paths makes "appears exactly once" true rather than likely.

### Added

- **Gap recovery: `updates.Manager` is wired.** Everything for it existed and was tested — `sqlite.StateRepo` implementing `updates.StateStorage`, `UpdatesDispatcher.Manager` — and nothing used it, so a mid-session transport drop left the mirror and the dialog list agreeing with each other and both stale. The manager is now the client's update handler, with the peer table as its channel access-hash store: it loads a channel's stored pts only when it can also find that channel's access hash, so the in-memory default would have quietly reduced recovery to private chats and basic groups after every restart. `MaxChannelDifferenceConcurrency` (new in gotd 0.161) is capped at 4 — recovery costs one `updates.getChannelDifference` per channel, and firing all of them the moment a connection returns is both rate-limit bait and a traffic shape no human client produces. The wiring is deliberately failure-tolerant: gotd documents `Handle` as forwarding updates as-is when `Run` has not succeeded, so a `getState` or storage failure costs ordering and gap recovery while live updates keep arriving, and the session is held open with the reason logged rather than torn down.
- `lazytg --polling` is documented in `README.md`, `docs/CONFIGURATION.md` and `docs/ARCHITECTURE.md` as what it now is, and `docs/MANUAL_SMOKE.md` gains a step that actually checks it (the previous one said the flag was a no-op and told the tester to skip).

### Security

- **The release toolchain is pinned to a patched Go.** `go.mod` declared `go 1.25.0` and nothing else, and every workflow installs from `go-version-file: go.mod` — so binaries shipped with whatever that resolved to, and `govulncheck` reported nine standard-library vulnerabilities reachable from this code, among them two in `crypto/tls`, one in `crypto/x509` and one in `net/http`. That matters for a client whose whole job is holding a long-lived TLS connection to a server it does not control. The `go` directive is now `1.26.6`, which takes the count to zero — verified by re-running the scan. It is the `go` line rather than a separate `toolchain` directive for a reason CI demonstrated: `setup-go` reads `go-version-file: go.mod` and installs the version on the `go` line, so a `toolchain` line below it means the action installs one Go and every subsequent command switches to another. The build cache restore then collided with the toolchain the switch had just downloaded (`tar: toolchain@v0.0.1-go1.26.6…/link: Cannot open: File exists`), leaving a cold cache, and the four-target snapshot build died on the runner without printing anything at all — twice, deterministically. One version on one line removes the switch, the collision and the rebuild together. Builders on an older Go download 1.26.6 automatically under the default `GOTOOLCHAIN=auto`. Of the remaining findings none is called by this code, and after the dependency sweep above none is in a third-party package at all.
- **A revoked authorisation no longer reconnects in a loop.** A session revoked from another device fails every attempt in exactly the same way, so treating it as retryable had the reconnect manager re-offer a dead auth key every backoff period for as long as the TUI stayed open. It is terminal now: the supervisor closes itself and the manager stops. Repeatedly presenting credentials Telegram has already invalidated is the kind of behavioural trace this project exists to avoid.

### Changed

- **The write probe could park the write lock on a pooled connection.** Making `ProbeWrite` dirty a page means it now holds an open transaction between `BEGIN IMMEDIATE` and `ROLLBACK`, and `modernc.org/sqlite`'s `ResetSession` returns nil without closing one — so any path that returned while the transaction was open handed the pool a connection still holding the write lock, and every later writer waited out the `busy_timeout` and failed for the life of the process. The rollback now runs from a deferred guard on `context.WithoutCancel(ctx)`: the probe's context is the application's, and cancelling it mid-probe is precisely when a cancellable rollback would not run. `TestProbeWrite_RepeatsCleanlyOnAReadOnlyDatabase` pins it — without the guard the second probe fails with "cannot start a transaction within a transaction" instead of reporting the read-only database. Found by the third review engine, and confirmed by reading the driver rather than by argument.

- **Homebrew delivery moves from a formula to a cask** before it ships anything: `goreleaser check` warns that `brews` is being phased out, and the tap has never received a formula (publishing is gated on a stable tag and only the alpha exists), so the migration costs nothing now and would have cost a `tap_migrations.json` and an upgrade path later. The cask carries a post-install hook that strips `com.apple.quarantine` — the binary is signed with cosign, which Gatekeeper knows nothing about, so without it every macOS install refuses to run on first launch. Verified by rendering it: a local snapshot writes `dist/homebrew/Casks/lazytg.rb` with the caveats, the `binary "lazytg"` stanza and the postflight block intact. One capability is lost — GoReleaser writes Linux URLs into the cask, but Homebrew on Linux refuses casks outright, so `brew install` becomes macOS-only in practice; Linux keeps the `.deb`, `.rpm` and archives the same release already publishes. Install and release docs say so rather than continuing to promise a Linux tap. They also state what the Homebrew route actually guarantees: Homebrew checks the SHA256 in a cask the pipeline itself commits, the cosign bundle is not verified on that path, and the quarantine strip removes Gatekeeper as the backstop — so the archive route in `docs/VERIFY.md` remains the one that checks a signature.

- **Every open dependency update applied in one sweep instead of nine merges** (Dependabot #3–#11): `gotd/td` 0.143.0 → 0.161.0, `modernc.org/sqlite` 1.50.0 → 1.56.0, `charm.land/bubbles/v2` 2.1.0 → 2.1.1, `golang.org/x/term` 0.42.0 → 0.45.0, `sahilm/fuzzy` 0.1.1 → 0.1.3, and the actions `checkout` 4 → 7, `cache` 4 → 6, `upload-artifact` 4 → 7, `goreleaser-action` 6 → 7. Five of the nine were red on CI, and the red was not theirs: they branched from `feea2ab`, which is `main` *before* the CI fixes, so their Lint job died on `invalid version string 'v2.0.2', golangci-lint v2 is not supported by golangci-lint-action v6` and their ubuntu test job on the 10-second `openTestRepo` budget — both already fixed here. Confirmed by reading the failing job's log rather than by inferring it from the base commit, because "red PR" and "bad bump" look identical from the outside.
- **The bubbles bump drags the whole Charm stack along.** `bubbles` 2.1.1 requires newer `bubbletea` (2.0.2 → 2.0.7), and minimal version selection then lifts `lipgloss` (2.0.2 → 2.0.4) and `charmbracelet/x/ansi` (0.11.6 → 0.11.7) as well. Named here because none of the three has an update PR of its own and all three carry code this project leans on: thread selection slices rendered lines with `ansi.Cut`, whose display-cell (not byte) indexing was established empirically against 0.11.6, and mouse handling reads bubbletea v2's `MouseClickMsg`/`MouseMotionMsg` types. The suite passes unchanged, including the tests that pin selection geometry against the rendered pane.
- **gotd 0.161 changes an option this project never set and adds two it will use.** `telegram.Options.Logger` is no longer a `*zap.Logger` but a `gotd/log.Logger` (bridging a zap logger now needs `logzap.New`) — nothing to migrate, since the client is constructed with `SessionStorage` and `UpdateHandler` only. Newly available: `OnConnectionState`, which reports `connecting`/`ready`/`disconnected` for the primary connection including gotd's own in-session reconnects, and a substantially reworked `telegram/updates` (per-channel difference concurrency limits, min-user backfill, `hook/affected`). Both bear directly on the remaining v0.1 gaps. The session storage format is untouched between the two versions, so an existing login survives the upgrade — checked by diffing the `session` package, not assumed.
- **The binary grows 21.0 → 23.4 MB (+11%), all of it inside gotd's dependency cone**: `refraction-networking/utls` arrives through `telegram/dcs` → `mtproxy/faketls`, and `yuin/goldmark` through `mtproto` → `testutil` → `ogen/gen`, which is a code-generation package reachable from non-test code upstream. Recorded because the install docs quote a size and because a 2.4 MB jump from a dependency bump is the kind of thing that is otherwise noticed only much later.
- **Action bumps checked against their breaking changes, not just against a green run.** `checkout` v6.1.0 blocks checking out fork PRs under `pull_request_target` and `workflow_run` — this repository uses neither trigger. `upload-artifact` v6 requires runner ≥ 2.327.1 (GitHub-hosted runners are past it) and v7's unzipped upload is opt-in via `archive: false`, so the snapshot workflow's multi-file glob keeps its current behaviour. `goreleaser-action` v7 is a Node 24/ESM rebuild, and PR #5 had already proven it against this repository's own config with a green GoReleaser snapshot job. Verified locally: `go build ./...`, `go test ./...`, `golangci-lint` 2.12.1 (0 issues) and `goreleaser check` all pass on the combined set.

First tagged build. Alpha: the pipeline that produces it has never run before this
tag, and the client itself has one live session behind it. Bring your own
Telegram API credentials (`LAZYTG_API_ID` / `LAZYTG_API_HASH`) and a test

### Added

- **Text selection in the thread, with copy to the clipboard.** Drag to select, release to copy; a drag inside one message is character-exact, and the moment it crosses into another message both are taken whole — the rule Telegram Desktop uses, and the one the user asked for ("выделяется сразу несколько целиком, даже если ты не до конца довёл"). A double click takes the message under the pointer, which is the common case without a precise drag. The highlight is reverse video (the one attribute every terminal renders identically) applied with cell-accurate, ANSI-aware slicing, so surrounding styling survives and the visible text is unchanged — `TestApplySelection_HighlightsWithoutChangingText` pins exactly that. Line ranges per message come from the renderer itself (`renderContent` returns content and spans together) rather than a second implementation of the same layout, because the two would drift and the drift would read as "it selects the wrong message". Copying goes through OSC 52 (`tea.SetClipboard`) instead of shelling out to pbcopy/xclip: it is the terminal's own clipboard channel, so it works over ssh and inside tmux with `set-clipboard on`, and lazytg needs to know nothing about the host. Whatever is highlighted is what lands in the clipboard, header row included when the selection covers whole messages — a character-exact drag inside one message is there for lifting out the text alone. A highlight is a range of screen cells with no tie to the text under it, so it is dropped wherever that text is replaced: opening another chat by any route, and any resize, including dragging the separator, which re-wraps every line (`TestSelection_DroppedWhenTheChatChanges`, `TestResizeDropsTheSelection`). The pane's own title row is inert, and a drag that actually selected something breaks the double-click pair, so pressing again on the same cell starts a new selection instead of copying the whole message.
- **Chat cycling: `ctrl+tab` / `ctrl+shift+tab` (aliases `alt+n` / `alt+p`) open the next and previous chat from anywhere, including mid-sentence in the composer.** Wraps at both ends and follows the list's own order — pinned first, then by last message, the same order Telegram shows. Both are ordinary keymap actions (`next_chat` / `prev_chat` in `keymap.toml`). The aliases are not decoration: `ctrl+tab` only reaches an application in terminals that implement key disambiguation (the Kitty keyboard protocol), and elsewhere the terminal sends a plain `tab`, which focus cycling takes.
- **The composer takes focus when a chat is opened**, from the click, the Enter, the palette and the search jump alike, so picking a conversation and typing in it is one gesture rather than two plus a Tab.
- **The pane separator is draggable.** The split is kept as an absolute column count (a ratio would make the pane creep on every resize), clamped so neither pane can be dragged into unusability, re-clamped when the terminal shrinks, and highlighted while held — a one-column grab handle gives no other feedback that the pointer caught it.
- **Mouse support: click a chat to open it, click a pane to focus it, wheel to scroll.** Reported from the first live session — "мышкой невозможно нажимать". The state before this was worse than an unsupported mouse: `View` already set `MouseMode = MouseModeCellMotion`, so the terminal handed mouse events to lazytg and stopped doing its own text selection, while not a single handler existed — clicks did nothing *and* dragging to copy was broken, with the cost of mouse capture paid for no benefit. Click routing lives in `internal/ui/app/mouse.go` on top of a new `computeLayout` (`internal/ui/app/layout.go`) that resizing and hit-testing now share, because two copies of the same pane arithmetic is how a click ends up one column off. Row-to-chat mapping is `chats.ItemIndexAt`: the offsets it relies on are bubbles' own (a title/filter line is drawn even with `SetShowTitle(false)`, and the default delegate spans two rows plus one of spacing), so `TestItemIndexAt_MatchesRenderedRows` derives the expected rows from the *rendered* pane — a bubbles upgrade that adds or drops a line fails a test instead of silently selecting the wrong conversation. A click and Enter go through one path (`SelectAt` → `handleEnter` → `ChatSelectedMsg`); the wheel scrolls without moving focus, since scrolling to read is not the same act as choosing where to type; horizontal wheels are ignored rather than reinterpreted as vertical; the separator column, the status row, overlays and the too-small-terminal fallback are all inert. The thread's wheel reuses the keyboard's pagination decision (`paginateAfterScroll`), so scrolling up with the wheel keeps loading older history instead of stopping dead at the loaded window and reading as "no more messages".
- **The TUI now talks to Telegram.** `runTUI` connects before building the UI (`cmd/lazytg/cmd/attach.go`): it picks the account (`--account`, or the only logged-in one — several without a flag is an error rather than a guess), opens the stored session, builds the update dispatcher, runs `Client.Run` in the background and calls `App.AttachClient` once the session is confirmed authorised. Connecting first is deliberate: the composer and thread panes capture their dependencies at construction, so attaching afterwards would mean mutating fields the Bubble Tea goroutine already holds. Every failure path — no session, no network, revoked authorisation, 20 s timeout — degrades to the cached-only view instead of refusing to start, and logs the reason so `--debug` explains an empty list.
- History now loads when a chat is opened. `App.requestHistory` (`internal/ui/app/update.go`) asks `BackfillService` for the chat's history from all three paths that open one — row pick, palette pick, search jump. Before this, `Backfill.Enqueue` was called from nowhere in production and the thread pane never invoked its history provider, so a freshly synced chat opened empty and stayed empty: the list would fill in while every conversation in it read as blank. The request runs off the update loop (Enqueue blocks on a full queue, and the Bubble Tea loop must never wait on I/O) behind an 8-slot gate — Enqueue takes no context, so a stopped consumer would otherwise accumulate one permanently blocked goroutine per chat opened. Re-opening a chat re-requests only when the local mirror is behind the dialog list (see the freshness check below); it used to re-request unconditionally, which recovered messages that landed while the process was elsewhere at the cost of one `messages.getHistory` per visit.
- Chat list retrieval, which did not exist before: `internal/tg/dialogs.go` (`messages.getDialogs` with position-based paging, decoding users/basic groups/supergroups/channels and joining titles, usernames, unread counts, pinned flags and top-message dates) and `internal/core/sync/dialogs.go` (`DialogsService`, which persists chats *and their access hashes* and publishes `DialogUpdated`). Until now `SaveChat` was called only from tests — the `chats` table stayed empty in real use no matter how healthy the connection was, so the left pane had nothing to render. Peers are written before chats on purpose: the UI reacts to `DialogUpdated` by reloading and may ask for history immediately, which needs the access hash.
- Live updates reach the UI: `ClientConfig.UpdateHandler` lets the cmd layer install the dispatcher at construction (gotd accepts an update handler only there), and `AttachClient` now adopts a pre-installed `App.Updates` instead of replacing it with a second dispatcher that nothing feeds.

### Documentation

- **Install docs described a release that does not exist.** The Quickstart opened with `brew install kar43lov/lazytg/lazytg`, and `docs/INSTALL.md` listed `.deb`, `.rpm`, signed archives and `go install …@latest` as supported paths — while `git tag` is empty, `gh release list` is empty, repository secrets are unset and the tap repository `kar43lov/homebrew-lazytg` does not exist. Anyone handed the project followed the first instruction into a 404. Both documents now lead with the two paths that work today (build from source; run a binary someone built for you), each release-fed path carries an *available once the first release is tagged* note, and `docs/RELEASE_PROCESS.md` records which preparation steps are still undone so the claim and the reality stay attached.
- **Decision: releases ship without Telegram API credentials, and the docs now say so everywhere.** The pipeline has always been able to embed a pair through `-ldflags`, and the repository secrets that would feed it are deliberately left unset. A key inside a public binary is a published key — `strings lazytg | grep -E '^[0-9a-f]{32}$'` prints it without knowing what to look for (measured) — and Telegram blocks published `api_id`s permanently, for every user of that build at the same moment, the maintainer included; recovery needs a new application, which needs a new phone number, since each number carries exactly one `api_id`. Their own instruction is *"obtain your own API id before you publish your app"*. `docs/SECURITY.md` replaces its "shipped credentials: the accepted risk" section with the reasoning for the opposite choice, `docs/INSTALL.md` and `README.md` no longer promise credential-free release installs, and the Homebrew caveats spell out the two exports.
- **`release.yml` no longer fails a stable tag when the credential secrets are unset.** It treated that as a misconfiguration and aborted, which would have turned the very first `v0.1.0` red under the model the project actually chose. Unset now emits a notice and proceeds; exactly one of the pair set still fails the release, because a half-built embedded layer makes `ResolveCredentials` report "build-time credentials are malformed (report this)" — an alarming error about a defect the user cannot fix.
- **Docs that were quietly wrong about the current build, found while making the credential decision consistent.** `docs/CONFIGURATION.md` listed the credential layer as "embedded in releases" in both the env-var table and the precedence table; `docs/TROUBLESHOOTING.md` told users a release would carry a pair; `docs/INSTALL.md` had a whole subsection built around a "shipped key" that no longer exists, now rewritten as *Running on someone else's key* (what you take on when the binary you were handed carries someone's `api_id`). The release announcement draft claimed live updates run through `updates.Manager` — v0.1 does not wire it, which is exactly why the freshness guard needs its expiry — and described sessions as living in the OS keyring, which stopped being true when they moved into `secrets.age`. A stale link to a plan that had moved into `docs/plans/completed/` is fixed too.
- **New: what to do when `my.telegram.org` will not issue credentials** (`docs/INSTALL.md`). The form is unreachable from some regions — from Russia it commonly never delivers the login code or answers a bare `ERROR` — so "just register your own" is not advice everywhere. Documented: registering once over a VPN yields credentials that keep working from anywhere afterwards, since the pair belongs to the account and not the network; or receiving a pair, or a binary carrying one, from someone who has one, with the shared blast radius stated for both sides.
- **New: how to give a working build to someone else** (`README.md` → *Sharing a build*, `docs/INSTALL.md` → *Building for someone else* and *A binary someone built for you*). Cross-compilation targets verified by building all four (`linux`/`darwin` × `amd64`/`arm64`, ~21 MB, statically linked, no cgo); the credential decision spelled out with its trade-off — compiling a pair in means everyone running that binary shares one `api_id` with you, readable back out with `strings`, and a flag lands on all of them at once; and the macOS reality that a hand-delivered Go binary is ad-hoc signed, gets quarantined in transit and is refused by Gatekeeper until `xattr -d com.apple.quarantine` (verified: `codesign -dv` reports `adhoc, linker-signed`). `docs/TROUBLESHOOTING.md` gains that failure and the `Exec format error` architecture mismatch, both stated as symptom → diagnosis → fix.

### Fixed (found during the first live session)

- **Text disappeared as the pane separator moved.** Both panes were sized to the full width of the box they are drawn in, while the box spends one column per side on padding: every full-width row was two columns too wide, lipgloss wrapped the overflow onto a new line, each wrapped item grew from two rows to three, and the rows below were pushed out of the frame — the last chat simply vanished. The panes now subtract the padding, and the minimum pane width is the panes' own floor *plus* that padding: at exactly 20 columns the chats list clamped itself back up to its own 20-column minimum and re-created the overflow at the one width where it was hardest to see. `TestFrameNeverOverflowsItsWidth` asserts the frame is never taller than the terminal (lipgloss wraps rather than overflowing, so height is where this shows) and fails on the pre-fix code at three different splits; its first version passed against the defect because the fixture's chat titles were too short to overflow anything.
- **Messages you had just sent carried no time and no author.** They render from the optimistic-outgoing path, which produced bare text while every message around them showed `[HH:MM] name` — reported as "неудобно", and it is: the row reads as a different kind of thing until the server echo replaces it, which can be the whole session when live updates never deliver one. Optimistic rows now go through the same header renderer, labelled `you`, with the state glyph (⏳ / ✗) in the header rather than in front of the body so the text column does not shift. The send time survives the state transitions, which previously rebuilt the row from scratch — losing the timestamp at the exact moment the message was confirmed sent.
- **Senders were rendered as `user-8385473863`, including your own messages.** Names now resolve from the chat list (which covers the other party of every private chat and any group with its own dialog row), falling back to the 1:1 rule — in a private chat a sender who is not the peer is the reader, so it says `you` without an extra RPC or self-id plumbing — and only then to the numeric id, which is all storage has for group members (`peers` keeps ids and access hashes, no names). The directory is the loaded chat list, so a conversation opened by a search jump that never made it into the synced 500 still shows numeric ids.
- **The chat list showed names over blank rows.** The preview was never populated (`NewChatItem(c, "")`), so the pane looked half-drawn. `GetChats` now returns each chat's newest cached message text through a correlated subquery riding the existing `(chat_id, date DESC)` index — one statement, not a query per chat — and newlines are collapsed, because a multi-line preview would push every row below it down and break the mouse hit-test's row arithmetic. Chats whose history is not cached yet still show a blank line; filling those needs the dialog sync to persist the top message it already receives.

- **Message timestamps were rendered in UTC.** Every layer below the UI keeps time in UTC deliberately — storage, the tg mapping, search — and the renderer formatted that instant as-is, so a message sent at 19:32 MSK appeared as `[16:32]`: three hours in the past, which reads as a stale thread rather than a formatting bug. Fixed in `internal/ui/panes/thread/format.go` and `internal/ui/panes/search/view.go`. The golden fixtures moved to `time.Local`, because a UTC fixture would have made the goldens pass only on a UTC machine (CI) and fail on every developer's; `TestFormatHeader_RendersInLocalZone` pins the conversion with an explicit +03:00 zone.
- **The status bar said `connecting` forever.** `statusbar.New` starts in that state and nothing in v0.1 ever moved it: `events.ConnectionStateChanged` is published only by `ReconnectManager`, which runs on reconnect attempts, never on the initial attach. So a fully working session showed a yellow `connecting` for its whole run and an offline one claimed it was still trying — the indicator carried no information at all. The state is now seeded from the attach outcome (`initialConnState` in `cmd/lazytg/cmd/tui.go`, keyed on `runtime.Client`, which `AttachClient` and nothing else sets).
- **Re-opening a chat re-fetched its history over the network.** The UI enqueues a backfill on every chat selection and `BackfillService` only coalesces requests still in flight, so moving focus back and forth cost one `messages.getHistory` per visit — six calls for two chats inside 25 seconds in the smoke log, with every message already in SQLite. `HistoryService.LoadInitial` now asks the new `Repo.ChatHistoryFreshness` whether the mirror already holds the newest message the dialog list knows about, and skips the fetch when it does. Timestamps rather than a remembered "already loaded this chat": a chat that gains messages mid-run compares as stale and is fetched again, where a remembered set would have gone quiet until restart — precisely how a thread stops updating without saying so. Any probe failure falls through to fetching, because a cache check that cannot answer must never be the reason history goes missing. The verdict also expires after 90 seconds, and that bound is what keeps the guard honest: both timestamps it compares live in local storage, so a transport drop freezes them together and the comparison would keep answering «current» for the rest of the run — with no `updates.Manager` in v0.1, the messages missed during the drop would then stay invisible until the next restart. Expiry restores the accidental recovery the unconditional re-fetch used to provide, at one `getHistory` per chat per window instead of one per visit (`TestHistoryService_LoadInitial_RefetchesAfterFreshnessWindow`). Found by review, not by use.
- **`lazytg login` never said where the code was sent.** The prompt was a bare `Code from Telegram:` while `*tg.AuthSentCode` carries the delivery channel, and the natural assumption — an SMS — was wrong: the code had gone to the Telegram app on the account's other devices as a service message. That cost several minutes of searching and two extra `SendCode` calls, each one more behavioural trace from an unofficial client. The prompt now names the channel (app / SMS / voice or missed call, including the "code is the last N digits of the caller number" case / email / Fragment / "configure a login email first"), and adds Telegram's own fallback when it offers one: `[not arrived? resend switches to SMS, allowed after 60s]`.

### Fixed (found reviewing this change)

- `AttachClient` is called from the goroutine that goes on to build the UI, not from inside the gotd session callback. Cancelling a context does not interrupt code already running, so a handshake completing just after the 20 s deadline would have wired services onto `App` while the caller was already reading the offline values into the panes — a data race, plus a half-attached session whose dialog sync never started and whose log claimed "opening on local cache". Attaching on the success branch of the caller's `select` removes the window by construction rather than by a well-placed check. A ready signal arriving in the same instant as the deadline is now honoured instead of discarded (`select` picks randomly among ready cases).
- The dialog cursor is captured from a single dialog. It was assembled from separate sources — peer from the last decoded chat, message id from the last raw entry — which disagree whenever the final entry was skipped for missing metadata; Telegram answers an inconsistent position with skipped or repeated pages. A dialog whose top message is absent from the response now ends the walk instead of paging on `int(time.Time{}.Unix())` = `-62135596800`, which Telegram reads as "from the beginning" and which turned the walk into a re-fetch of page one. A cursor that fails to advance also ends the walk rather than spending the remaining page budget on identical requests.
- Session teardown waits (up to 2 s) for the session goroutine to unwind before the caller closes the database, and a session that ends mid-flight is logged — reconnect is still a stub, so the services stay bound to a dead client, and without that line the user sees sends failing with no stated cause.
- `NewBackfillService`'s error is logged instead of discarded, and the dialog walk states why it stopped: a page that came back full but carried no usable cursor means the list was truncated, which otherwise looks exactly like "these are all your chats".
- Dialog sync is bounded — 100 dialogs per call, 5 pages, 300 ms between pages. The cap and the spacing are ban-risk measures, not performance tuning: five back-to-back `getDialogs` calls in a few hundred milliseconds is not what a human opening an app looks like.

- `scripts/secret-scan.sh --self-test`, run in CI before the scan itself. The gate leaked during its own review: the first pattern anchored on neighbouring non-hex characters, and since `grep -o` cannot restart a match on a character it already consumed, only the *first* hex run per line was ever reported. A line holding the documentation placeholder followed by a real key therefore surfaced only the placeholder, which the allowlist then dropped — the credential passed the gate silently. The pattern now matches `[0-9a-f]{32,}` and filters to exactly-32 afterwards (still rejecting sha1/sha256 digests), and the self-test pins that exact case. A scanner that quietly stops matching reports "clean" indistinguishably from one that found nothing, which is why the rules are now verified before their verdict is trusted. The same review found the scanner printing `clean` and exiting 0 when run outside a git repository at all — `git ls-files` failure was swallowed by the pipe — so both collectors now check git's exit status and abort with a distinct code instead. Staged scanning reports the filename (it previously printed a line number counted through the whole concatenated diff, pointing at nothing), CRLF files are no longer a blind spot, and the gate's known limits — obfuscated keys, uppercase hex, keys glued to longer hex runs, binaries, anything already on main — are documented in the script header and pinned by self-test cases.

A tree scan only sees the branch tip, which misses the likeliest real leak: a key committed, noticed, and deleted in a follow-up commit — tip clean, key still riding into main in the history, which is exactly what Telegram treats as published. ### Fixed

- 🔴 **Sessions were never persisted on macOS, so the app could not work past a single process.** Found on the first live login. A gotd session blob is ~4.2 KB (auth key plus the full DC configuration), and `zalando/go-keyring`'s macOS backend builds a `security -i` command line that it refuses past 4096 bytes (`ErrSetDataTooBig`). The failure was anything but graceful: gotd calls `StoreSession` from inside connection setup, so the rejected write tore the connection down and the in-flight auth-status RPC failed with `engine forcibly closed: context canceled` — while `lazytg login` printed `logged in as …` regardless, because gotd's `Run` returned nil. Symptom for the user: login "succeeds", Telegram shows a new device, and every subsequent start opens on the local cache with a cryptic transport error in the log. Unit tests could not see it — they inject their own storage, and the keyring's limit only exists in the real backend. Secrets now live in `<config>/secrets.age` and the keyring holds only the passphrase that opens it, generated once so a desktop user is never prompted; headless boxes keep prompting as before. Verified end-to-end: the same handshake that used to die now saves a 4197-byte session and reads it back. Pinned by `TestSecretStore_HoldsSessionSizedValue`, `TestKeyringStore_RejectsSessionSizedValue` (which documents the limit that forced the design) and `TestKeyringPassphrase_GeneratesOnceAndReuses` (a provider that minted a new passphrase per call would be a silent logout). Cost: `age`'s scrypt adds ~390 ms to a session write and to the first read after start, against a 20 s attach budget. Because the store is a single ciphertext, every write rewrites every key — so writes now take an exclusive `flock` on a `secrets.age.lock` sidecar and re-read the file inside it, otherwise `lazytg login --account other` running next to a live TUI would silently drop the TUI's session on its next refresh (`TestAgeFileStore_ConcurrentProcessesKeepBothKeys`; the lock is a sidecar because the atomic rename swaps the data file's inode). A passphrase that no longer opens the file is refused rather than "recovered" — re-encrypting under it would destroy the only copy of the session (`TestAgeFileStore_WrongPassphraseIsNonDestructive`), so the error now names the remedy and `docs/TROUBLESHOOTING.md` documents it.
- **Concurrent writes were being lost.** No `busy_timeout` pragma was configured, and SQLite allows exactly one writer at a time: a connection that found the write lock taken failed its statement instantly with `SQLITE_BUSY` instead of waiting. lazytg writes from several paths at once by design — live drain, history backfill, dialog sync, FTS reindex — so this was not a rare race. Measured on a burst of 4 goroutines × 300 writes, **973 of the 1200 failed**. The user-visible symptom would have been messages that simply never appear, with a healthy disk and nothing in the log to explain it, and the first live smoke would have walked straight into it. `pragmaQuery` now sets `busy_timeout(5000)`; the same burst loses nothing. `TestConcurrentWriters_NoBusyFailures` reproduces the shape at 4 × 150 — smaller only to stay quick — and asserts zero failures. The timeout has room: the largest single write transaction in the app, a 5000-row `Indexer.Backfill`, was measured at 151 ms.
- **A write burst could put the whole repo into read-only mode.** `Repo.ProbeWrite` issues `BEGIN IMMEDIATE`, which needs the write lock, and `DegradationDetector` turns any probe error into soft read-only mode where every write returns `ErrReadOnly` until a later probe recovers. `SQLITE_BUSY` was treated as such an error — so a probe landing inside a write burst disabled all writes for up to the 30 s probe interval and told the user the filesystem was read-only. Contention is now reported as success, which is what it means: another connection holding the write lock is positive evidence that the storage accepts writes. No genuine failure code masks into that classification — `SQLITE_PERM` (3), `SQLITE_READONLY` (8), `SQLITE_IOERR` (10), `SQLITE_CORRUPT` (11), `SQLITE_FULL` (13), `SQLITE_CANTOPEN` (14) and `SQLITE_NOTADB` (26) each keep a low byte of their own — so degradation detection keeps whatever coverage it had. Pinned by `TestProbeWrite_ToleratesContention`, `TestProbeWrite_ReportsNonContentionFailure` and `TestIsContention_ClassifiesResultCodes` (the code table, including extended codes — the driver enables those on every connection, so masking is required rather than defensive). This surfaced as `Memory budget gate` failing on `main` with `seed corpus: save chat 7: repo: read-only mode`.
- Documented a **pre-existing gap found while reviewing the above**, rather than left implied: `ProbeWrite` cannot detect a read-only database at all. `BEGIN IMMEDIATE` takes the write lock but dirties no page, so SQLite never raises `SQLITE_READONLY` and the probe reports healthy storage while ordinary writes fail with "attempt to write a readonly database" — verified against the previous revision, where the probe returned `nil` just the same. `DegradationDetector` therefore misses the one condition it was written for, and the doc comment claimed the opposite. Corrected in the comment and in `docs/ARCHITECTURE.md`, and pinned by `TestProbeWrite_KnownGap_ReadOnlyDatabaseUndetected` — whose assertion is inverted, so it passes while the gap exists and fails the moment someone closes it. Not fixed here: the fix belongs with the detector, and `DELETE FROM chats WHERE 0` inside the probe transaction was measured to raise `SQLITE_READONLY` (8) while touching no rows.

- Optimistic-UI flicker race: `applyOutgoingState{Pending}` is now a no-op so the bus event cannot insert an empty `[⏳]` row before `SendDispatchedMsg` (carrying the message body) lands.
- `SendFailedMsg` no longer clobbers a fresher draft or retargeted reply pointer when the user moved on while the failed send was in flight — the failure is dropped and surfaced as a warn log.
- Configurable `ScrollUp`/`ScrollDown` chords (default `ctrl+b`/`ctrl+f`) now actually scroll the thread viewport when the thread or chats pane is focused; previously the chord was advertised in `keymap.toml` and the help overlay but no code consumed it.
- `LiveService.persist` no longer republishes `DialogUpdated` onto its own subscription — the chats pane reacts to `MessageReceived` directly, which removes the buffer halving and the resulting potential for dropped events under burst.
- `?` (default `ToggleHelp` chord) no longer hijacks the input pane or the chats filter: when the input pane is focused or the chats list is in filter-input mode the keystroke falls through to the focused widget. Previously a question mark could not be typed into the message body or chat-list filter.
- Reply-preview truncation in the input pane is now rune-aware: a Cyrillic / CJK reply target longer than 50 codepoints is cut on a codepoint boundary instead of being byte-sliced mid-UTF-8. The byte-slice path emitted invalid UTF-8 to the terminal for the project's primary audience (Russian-speaking users).
- Optimistic row no longer disappears between `Sent` and the live echo: `applyOutgoingState{Sent}` flips the row's state in place (rendering as plain text without the `[⏳]` glyph) and `applyIncoming` removes it on the server-echo `MessageReceived`. Private 1:1 chats — where Telegram emits `UpdateShortSentMessage` instead of a follow-up `UpdateNewMessage` — therefore keep the user's message visible until manual reload.
- Inverted-race guard: a `SendDispatchedMsg` arriving after a terminal `Sent` or `Failed` bus event no longer re-creates a Pending row. The thread now records every finalised localID and short-circuits the late insert that would otherwise leave a phantom `[⏳]` no future event could resolve.
- Async send failures (FloodWait, validation, network retries exhausted) now restore the textarea body and reply pointer just like the synchronous-error path. The input pane stashes the dispatched body keyed by `LocalID` and reacts to `OutgoingMessageStateChanged{Failed}` on the bus; previously the CHANGELOG promise of "Failed sends restore the draft" only held when SendService returned an error before publishing — i.e. for the rare optimistic-store-write failure surface.
- Repeated `Ctrl-D` on the same media no longer spawns overlapping `DownloadService` goroutines that would race over the shared `<path>.partial` and corrupt the output. The app now reserves the `FileID` for the lifetime of the goroutine; a second chord while the first is in flight is a quiet no-op (debug-logged).
- Search overlay `Enter` now loads the matched message's ±5 context window via `search.Service.JumpContext` and scrolls the thread to the hit — even when the target message is older than the freshly-loaded initial-page slice. Previously the jump opened the chat at its newest 200 messages and the deferred `ScrollTo` silently no-op'd whenever the target was not in that window (the prime FTS5 use case for old hits). On a `JumpContext` error the path falls back to the legacy `OpenChat + deferred ScrollTo` so the user still lands in the chat.
- Search-jump no longer strands the user in an isolated ±5-message slice: the thread pane now exposes symmetric forward pagination (`Repository.GetMessagesAfter` + `applyPaginationNewer` + `AtBottom + hasNewer` trigger). Scroll-down at the bottom of the loaded window walks the model toward the present so messages newer than the window are reachable without re-opening the chat.
- Search-jump now resists stale repo loads: a slow `OpenChat` fetch (or in-flight older-page pagination) for the same chat can no longer clobber the freshly-installed jump window. The thread model carries a `loadGen` counter bumped on every `OpenChat` / `SwitchTo` / `LoadJumpWindow`; `loadCmd` / `paginateCmd` / `paginateNewerCmd` capture it at scheduling time and the matching apply-handlers drop messages whose generation no longer matches.

### Known gaps (Stage 2 + Stage 3 follow-up)

- **The chat list is ordered by a date only dialog sync maintains.** `chats.last_message_date` is written by `SaveChat`, and nothing on the live path updates it — so a message arriving in an existing chat does not move that chat up the list until the next sync. `EnsureChat` seeds the column for a chat it creates, which fixes the new-chat case at the moment of discovery, but a backlog delivered oldest-first after a reconnect leaves the row stamped with the oldest message of the batch. Found by review on 19.08.2026; left alone deliberately, because the fix belongs with the ordering path rather than inside a function whose job is to create a missing row.

- Search overlay renders `chat=<id>` instead of the chat title — the overlay does not yet take a chat-title source. Cosmetic but UX-degrading on the killer feature.
- `from:@username` resolves through `chats.username` — a user whose row is not in `chats` (most group/channel senders) silently produces zero hits. Documented in `docs/SEARCH.md`; full fix needs a peer-username index.
- `in:#chatname` only accepts a single whitespace-bounded token, so multi-word chat titles cannot be expressed via the operator (`in:#general` works, `in:#"Family Group"` errors and `in:#Family Group` filters by `Family` only). Parser v0.1 splits tokens before applying operators; quoted-value-after-operator support is deferred to Stage 4+. Workaround: filter by `username` when the chat has one. Documented in `docs/SEARCH.md`.
- ~~Reconnect, gap recovery and the polling fallback have never faced a real outage.~~ **Closed 19.08.2026** by the first live smoke, which is also what found the four defects listed under Unreleased. The link was cut with both interfaces down: the indicator went offline and back, and messages sent during the outage arrived on their own. Gap recovery specifically was not merely untested but broken — see the `state` foreign key above. What the smoke still has not exercised is the manager's own session restart: gotd recovered internally, so `ReconnectManager.Run` never had to stand a new session up.
- ~~Foreign-key cascade (`messages.chat_id REFERENCES chats(id)`): `LiveService.persist` still does not upsert a chat row, so a message from a chat outside the synced page window has no parent row.~~ **Closed 19.08.2026** — `EnsureChat` creates it. The gap was also underestimated here: it did not take a chat beyond the 500-dialog window, only a first message from a new contact. `DialogsService` covers the first 500 dialogs, which makes this rare rather than fixed.
- Dialog sync stops after 5 pages (500 chats) by design — an unbounded crawl is the access pattern the ban-risk policy avoids. Accounts past that see their remaining chats only once those chats receive a message.
