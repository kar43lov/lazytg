# Search & FTS5 index (Stage 3)

Документ описывает локальный поисковый pipeline lazytg: query syntax, поведение индекса, ёмкость БД, ограничения и SLA.

Соответствующие пакеты: `internal/core/search/`, `internal/storage/sqlite/migrations/0005_fts.sql`, `internal/ui/panes/search/`.

---

## Query syntax

Поиск открывается клавишей `/` (Search keymap) поверх любого pane. По мере ввода (debounce 150ms) overlay показывает совпадения; Enter переходит в нужный чат и скроллит к контексту ±5 сообщений.

### Базовый поиск

| Что вводится       | Что находится                                                                 |
|--------------------|-------------------------------------------------------------------------------|
| `привет`           | Сообщения с подстрокой `привет` (трёхграммный токенайзер, см. ниже)           |
| `hello world`      | Сообщения, содержащие оба слова (`AND` неявный)                               |
| `"exact phrase"`   | Точная фраза в кавычках. Внутри — `\"` escape для буквальной кавычки          |
| `-spam`            | Исключение слова длиной ≥ 2 символа: результат **не должен** содержать `spam` |

### Операторы

| Оператор             | Эффект                                                                  |
|----------------------|-------------------------------------------------------------------------|
| `from:@username`     | Только от пользователя с указанным `username` (без `@`-префикса в БД)   |
| `in:#chatname`       | Только в чате с указанным `username` или `title`                        |
| `before:2026-01-01`  | До этой даты (UTC, exclusive)                                           |
| `after:2025-12-01`   | После этой даты (UTC, inclusive)                                        |
| `before:2026-01-01T15:00:00` | С точностью до секунды (UTC)                                    |
| `has:file`           | Только сообщения с медиа-вложением (`media_kind` IS NOT NULL)           |

Время — UTC. Парсер использует `time.ParseInLocation` с `time.UTC` так что `before:2026-01-01` означает «до 2026-01-01 00:00:00 UTC».

`has:` принимает только значение `file`. Любое другое (`has:photo`, `has:link` …) вернёт ошибку парсинга — это место расширения в будущих версиях.

### Kitchen-sink пример

```
"hello world" from:@alice in:#dev before:2026-01-01 has:file -spam
```

Найти точную фразу `hello world` в сообщениях от `@alice`, в чате `#dev`, отправленных до 2026-01-01 UTC, с прикреплённым файлом, исключая сообщения со словом `spam`.

### Что НЕ поддерживается в v0.1

| Что               | Когда                                                                     |
|-------------------|---------------------------------------------------------------------------|
| Saved searches    | v0.5+ (smart folders / tgql)                                              |
| Stemming русского | См. ограничения ниже                                                      |
| OR-операторы      | v0.2 (`A | B` через FTS5 native syntax) — пока только неявный AND        |
| Префиксный поиск  | v0.2 (`prefix*`) — trigram плохо ловит коротких префиксов                 |
| Reactions/edits   | v0.3 — таблицы пока не индексируются                                      |

## Tokenizer и индексация

**Токенайзер:** `trigram` (встроенный в SQLite ≥ 3.34, language-agnostic).

Trigram разбивает строку на пересекающиеся 3-грамма code-points, что:

- работает одинаково хорошо для русского, английского, эмодзи, китайского
- обходит отсутствие ICU в `modernc.org/sqlite` (CGo-only расширение)
- даёт substring-поиск из коробки (`привет` находит и `Привет!`, и `подвальный`-внутри `подпривет` если бы такое существовало)

**Минимальная длина:** trigram **не индексирует строки короче 3 code-points**. Запрос `ok` (2 символа) даст 0 результатов даже если в БД есть сообщение `ok`. Это знаемое поведение FTS5 — не баг.

**Case-insensitive:** опция `case_sensitive 0` (миграция 0005). Поиск `при` находит `Привет`. Не нужен префолдинг на стороне Go.

**Стандартная схема (миграция 0005):**

```sql
CREATE VIRTUAL TABLE messages_fts USING fts5(
    text,
    tokenize = 'trigram case_sensitive 0',
    content = ''        -- standalone (не external content) — см. план Stage 3 Task 1
);
```

Standalone schema выбран сознательно вместо external `content='messages'`: external content table возвращала бы все rowid из `messages`, ломая idempotent-проверку `Backfill` (она опирается на `WHERE rowid NOT IN (SELECT rowid FROM messages_fts)`).

Накладные расходы: текст дублируется между `messages.text` и `messages_fts.text`. На 100k сообщений × ~80 байт текста это ~8 МБ — копейки на фоне 3-5× overhead самого FTS-индекса (см. ниже).

**Триггеры:** AFTER INSERT / AFTER UPDATE / AFTER DELETE на `messages` поддерживают `messages_fts` в синхронизации автоматически. Миграция 0005 создаёт их вместе с таблицей.

## Lazy index и backfill

**Default cap:** последние **5000 сообщений на чат** индексируются автоматически (`internal/core/search/lazy.go::DefaultPerChatLimit`). Триггер срабатывает на первый поиск в сессии — не на старт приложения.

Это компромисс между:

- **Скоростью первого старта:** полная переиндексация 1M сообщений на холодной БД заняла бы минуты.
- **Полнотой:** 5000 последних — это типично последние ~3 месяца чата, что закрывает 80%+ запросов.

**Полная переиндексация:**

```sh
lazytg reindex --all          # все чаты, целиком
lazytg reindex --chat 12345   # один чат, целиком
```

Команда работает в stderr (TUI не запускается), поэтому подходит для cron / однократных миграций. Прогресс-events `ReindexProgress` идут в шину и видны в `--debug` логах.

> Команда вызывает permissions-audit (`app.CheckPermissions`), открывает репо и запускает `ReindexService.Run`/`RunAll` напрямую — прогресс льётся в stderr, чтобы скрипты могли его перехватывать. p95 search latency на 100k сообщений отслеживается в CI через `make bench` (BenchmarkSearch100k самофейлит при p95 > 100 ms).

**Cancel-safety:** `ReindexService.Run(ctx)` корректно прерывается на `ctx.Done()`. После cancel БД остаётся в консистентном состоянии (`PRAGMA integrity_check` = `ok`); проверено в `internal/core/search/reindex_test.go::TestRunAll_GracefulCancel`.

## Ёмкость БД и trigram overhead

Trigram — самый «толстый» из встроенных токенайзеров FTS5 (porter / unicode61 экономнее, но не работают для русского без ICU). Реалистичные оценки:

| Сообщений в БД | Размер `messages_fts` (примерно) | Размер всей БД |
|----------------|-----------------------------------|----------------|
| 10k            | 5–20 МБ                           | ~30–50 МБ      |
| 100k           | 50–200 МБ                         | ~250–400 МБ    |
| 500k           | 250 МБ – 1 ГБ                     | ~1–2 ГБ        |
| 1M             | 500 МБ – 1.5 ГБ                   | ~2–3 ГБ        |

Точное значение зависит от длины сообщений (короткие сообщения дают худший ratio: trigram-overhead растёт быстрее текста) и доли латиницы/кириллицы.

**DB size warning** (Stage 3 Task 8): когда файл `lazytg.db` превышает **1 ГБ**, status bar показывает `⚠ DB N.N GB` в правой части. Это информационное предупреждение — БД продолжает работать, индекс продолжает обновляться. Опции реакции:

- ничего не делать, если 2 ГБ диска не критичны;
- `lazytg reindex --all` после изменения `DefaultPerChatLimit` (Stage 4 даст конфиг через `~/.config/lazytg/lazytg.toml`);
- удалить БД и начать с пустой (`rm ~/.local/share/lazytg/lazytg.db` — потеряет локальную историю и frecency, но не сессию).

Порог настраивается через `obs.DBSizeConfig.Threshold` при wiring (Task 10 подключит к `wire.go`).

## SLA и benchmark

**Целевая p95 latency:** **< 100 мс на 100k сообщений**. Гарантия — benchmark gate в CI:

```sh
go test -bench=BenchmarkSearch100k -benchtime=1x ./internal/core/search/
```

Benchmark создаёт реалистичный корпус (20 чатов × 5000 сообщений, текст 3–18 слов с детерминированным PCG seed=42), warm-up кэша, 100 итераций по варианту запроса (`привет`, `hello world`, `тест`, `abc def`). Падает с `t.Fatalf` если `latencies[len*95/100]` > 100 мс.

Текущие замеры на M4 (см. план Stage 3 Task 2):

- p50 = 37.7 мс
- p95 = 44.2 мс
- p99 = 45.0 мс

Запас по SLA ~2.3×. Регрессии ловятся в CI до merge.

## Ограничения

| Ограничение                                  | Workaround                                                |
|----------------------------------------------|------------------------------------------------------------|
| Нет stemming для русского                    | Искать обе формы: `сообщение OR сообщения` (через два запроса в v0.1) |
| Trigram не находит строки короче 3 символов  | Использовать более длинный запрос                          |
| `before:` / `after:` только в UTC            | Конвертировать руками до запроса                           |
| Нет saved searches / smart folders           | v0.5+; пока — alias на shell-команду через query string    |
| Нет OR-оператора                             | Два запроса в v0.1; v0.2 даст native FTS5 OR               |
| Reactions / edits / forwards не индексируются| Только `text` в `messages` попадает в `messages_fts`       |
| `from:@user` находит только тех, чей peer записан в таблицу `chats` с заполненным `username` | В v0.1 это работает для приватных диалогов и ботов с username; отправители в группах/каналах без отдельного user-индекса не находятся (тихий 0 результатов). Полный фикс — отдельная таблица `users` в Stage 4+. |
